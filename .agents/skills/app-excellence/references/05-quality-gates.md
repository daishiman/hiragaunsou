# 05. Quality Gates — 体験QA・性能検証・リリース判定

CIの機械ゲート(型・テスト・脆弱性・アクセス制御)は Skill testing-excellence / launch-security が担う。本プレイブックはその上の**体験の品質**を検査する。合格基準は「デモで恥ずかしくないか」ではなく「**最悪条件のユーザーが目的を達成できるか**」。

## §1. バグの重み定義(直す順番を迷わない)

- **Blocker**: 主要ジャーニーが完了できない/データ消失/権限越え → リリース不可・即修正
- **Critical**: 回避策はあるが主要ジャーニーが著しく損なわれる/誤解を生む表示 → リリース前に修正
- **Major**: 副次ジャーニーの障害・6状態の欠落 → 原則修正、遅延時はT4にリスク受容を記録
- **Minor**: 見た目の乱れ・文言 → 記録してSlice 2+へ

## §2. 体験QAウォークスルー(スクリプト化された「意地悪な一周」)

リリース候補ごとに以下を**実際に操作して**通す(Playwright化できるものはE2Eに昇格させる):

1. **初回の5分**: 新規ユーザーとしてサインアップ→Ahaモーメント到達まで。迷った秒数・読まされた文字数を記録
2. **空の世界**: データゼロの全画面を巡回(空状態が行動を促しているか)
3. **意地悪入力**: 全フォームに 空/最大長/絵文字/機種依存文字/全角数字/前後空白 を投入
4. **低速と切断**: 3G相当のスロットリングで主要ジャーニー一周/送信中に機内モード→復帰(データが消えないか)
5. **中断と再開**: 入力途中でタブを閉じる・アプリを切り替える→戻って続きから再開できるか
6. **端末マトリクス**: 小型スマホ(SE級 375px)/標準スマホ/PC。文字200%拡大でレイアウトが破綻しないか
7. **二重操作**: 送信ボタン連打・戻るボタン・同一ユーザー2タブ同時編集
8. **権限の壁**: 他人のデータのURLを直叩き(アプリ層のアクセス制御が効いているかの実地確認)/ログアウト状態で保護ページへ

## §3. チェックリスト検査

references/checklists/ の4ファイル(ux-psychology / performance / accessibility-jp / risk)を全項目検査し、結果をT4に添付する。不合格項目は修正するか、依頼者に説明の上で「リスク受容」として記録する(黙って落とさない)。Sサイズ案件は★印の項目のみで可。

## §4. リリース判定(T4)

assets/T4-release-readiness.md を埋め、以下が全て Yes なら Go:

- [ ] T1の成功指標を計測するイベントが本番で発火する状態にある
- [ ] §2ウォークスルーで Blocker/Critical ゼロ
- [ ] §3チェックリスト: 全通過 or リスク受容が文書化済み
- [ ] ロールバック手順が自動で機能する(CI側で確認済み)
- [ ] 依頼者がプレビューで受け入れ確認済み(非IT依頼者の場合は「リリースして」の明示発話をもって確認とする)
- [ ] リリース後1週間のレビュー日が決まっている

**Apple基準の最終問診**: 「この体験を、明日の全社デモで自分が操作して見せられるか?」— Noなら理由がBlockerである。
