# 01. Requirements — 要件を「機能の羅列」ではなく「5層」で分解する

要件定義の失敗パターンは決まっている: 依頼者の口から出た「機能」をそのまま作ること。人は解決策の形で課題を語る(「CSV出力機能が欲しい」の正体は「上司への月次報告が苦痛」)。あなたの仕事は**5層に分解して、機能の一つ上の層から設計し直す**ことである。

## §1. 5層分解モデル(上から順に確定させる)

| 層 | 問い | 例(日報アプリ) |
|---|---|---|
| L1 課題 | 誰が、いつ、何に困っているか(Job to be Done) | 営業8名が毎夕、日報の記入と転記に計40分/人かかる |
| L2 成果 | 解決されたら何がどう変わるか(数値) | 記入5分以内・集計ゼロ分。月20時間の創出 |
| L3 行動シナリオ | to-beの一日はどう流れるか | 訪問直後にスマホで30秒入力→夕方は何もしない→月初に自動集計を確認 |
| L4 体験要件 | その行動が自然に起きるための体験条件 | 移動中に片手30秒で完了/入力済みが一目で分かる/未入力の督促は本人だけに |
| L5 機能要件 | 体験を実現する最小の機能 | クイック入力フォーム/自動集計/リマインド通知 |

**規律**: L5から会話が始まったら、必ずL1〜L2に遡って確認する。L1に戻せない機能要望は「保留リスト」へ(拒否ではなく、根拠待ち)。

## §2. ヒアリングプロトコル

1. **現状再現**: 「昨日、その作業をしたときのことを最初から話してください」(一般論でなく直近の実例を取る。実例にしか真実はない)
2. **痛点の定量化**: 頻度×所要時間×関係人数。感情語(「面倒」「怖い」)は体験要件の宝なのでそのまま記録
3. **成功の定義**: 「3ヶ月後、これが大成功だったと言えるのはどんな状態ですか?」→ L2の数値に変換
4. **ユーザー分類**: 主要ユーザー/副次ユーザー/管理者/(いれば)社外。それぞれの利用頻度と習熟度
5. **Non-Goals**: 「今回やらないこと」を最低3つ、依頼者の口から引き出して合意する(後の期待値事故の9割はここで防げる)
6. **制約**: 期限・予算・既存ツール・扱う情報の機微度(決済・マイナンバー・要配慮個人情報・基幹システム書き込みに該当する場合はプロジェクトのガードレール規定に従いIT担当へエスカレーション)

## §3. 成功指標の設計(Netflix流: 感覚でなく計測)

- **North Star(1つだけ)**: L2の成果を直接表す指標(例: 日報起点の総作業時間/週)
- **ガードレール指標(1〜3つ)**: 改善の副作用を監視する指標(例: 入力率が下がっていないか、入力の質が落ちていないか)
- 各指標に: 現在値 / 目標値 / 計測方法(どのイベントで測るか)を必ず添える。**計測できない指標は指標ではない**
- 計測イベントはPhase 4で機能と同時に実装する(references/04-build-standards.md §5)

## §4. 非機能要件(NFR)の既定値 — 聞かずに適用し、逸脱だけ確認する

依頼者にNFRを質問しない(答えられない)。以下を既定値として適用し、逸脱が必要な場合のみ提起する:

- 性能: checklists/performance.md の予算
- セキュリティ: Skill better-auth-google-gate / launch-security の必須実装(認証・アプリ層でのアクセス制御・監査ログ)
- アクセシビリティ: checklists/accessibility-jp.md(WCAG 2.2 AA相当)
- 可用性: 業務時間内の障害は15分以内に自動ロールバックで復旧(CI設計に内包)
- データ: 日次バックアップ/削除はゴミ箱方式/保持期間は依頼者確認

## §5. T1(要件定義書)への着地

assets/T1-requirements.md を複製して埋める。**ゲート条件**: L1が一文で書ける/L2が数値/Non-Goals3つ以上/全ユーザー分類に利用頻度がある。埋まらない欄は埋まらないまま依頼者に見せて確認する(勝手に補完しない)。
