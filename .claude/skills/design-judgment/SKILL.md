# Design Judgment — 「判断のあるUI」を作るための診断フレームワーク

> AIっぽいUIは、UI部品の平均値を並べた画面。
> AIっぽくないUIは、業務の構造がそのまま画面の構造になっている。

「AIっぽさ」は制作手段の問題ではない。**明確な設計判断(何を最優先に見せるか・何を隠すか・何を隣に置くか・どこを固定するか・どの操作を一手で終わらせるか・エラー時にどこへ戻すか)が見えるかどうか**の問題である。したがって本スキルは「こうしろ」という完成形のルール集ではなく、**その判断を下すために何を調べるべきかという問いの集合**として作られている。問いに自分で答え、答えに応じて構造を選ぶのはAI自身の仕事であり、この自由度を奪わない。

このスキルは4つのPhaseを順に通過する。各Phaseは**チェックボックス形式の問い**で構成される。「はい/いいえ」で終わらせず、**答えを1行の言葉にして残す**こと(言葉にできない項目は、まだ判断していないという合図)。

## Phase 1 — 業務構造を発見する(最初に、必ず)

テンプレートから始めると業務構造は現れない。**扱う対象を先に決めてから画面を考える。**

- [ ] この画面でユーザーが実際に手を動かして扱う**中心的な対象(名詞)**は何か。それを一言で言えるか(「案件」「注文」「申請」「原稿」「予約」など、機能名ではなく業務上の名詞)。
- [ ] その対象を、ユーザーは1日/1回の作業で**何件・何回**扱うか。件数や頻度によって、一覧向きか・単票向きか・比較向きかが変わる。数を把握せずに形式を決めていないか。
- [ ] ユーザーがこの画面で行う**最頻の操作**は何か。上位3つを具体的な動詞で言えるか(「確認する」ではなく「担当者を変更する」のように)。
- [ ] その最頻操作のうち、**現状ページ遷移やモーダルを経由しないと完了しないもの**はどれか。一手で終わらせられないか検討したか。
- [ ] この画面の**主役**(最大の面積・最初に視線が行く場所)は何か。それは「ユーザーが今から扱う対象」であって、装飾的な集計や紹介文になっていないか。
- [ ] 数値やグラフを置くなら、それは**次に取るべき行動に接続しているか**(「見て終わり」の数字になっていないか)。

## Phase 2 — 何を主役にし、何を隠すか判断する

判断が見えるUIとは、要素の強さに差がある状態のこと。**差がなければ、それは判断していないのと同じ。**

- [ ] 画面内のすべての箱(カード・パネル・枠線)について、**なぜその境界が必要か**を言えるか。余白のグルーピングだけで意味が伝わるなら、枠は要らない。
- [ ] 角丸・影・色の強さといった装飾的な性質を、**同じ画面内のすべての部品に均一に適用していないか**。押せるもの・選択できるもの・状態を表すものそれぞれに、意味の違いとして形の違いを与えているか。
- [ ] 視覚的な強さ(サイズ・コントラスト・余白・配置)を、**画面全体で一様にしていないか**。すべてを目立たせると、何も目立たなくなる。
- [ ] 比較・走査・判断など、**行うタスクの種類ごとに情報密度を変えたか**(比較する場所は密に、確認・編集する場所は余白を多めに)。密度を画面全体で一定にしていないか。
- [ ] 頻繁に使う操作を、ホバーやメニューの奥に**隠しすぎていないか**。「見た目の静けさ」と「操作の発見可能性」を混同していないか。
- [ ] ラベルや見出しの文言は、**この業務で実際に使われる言葉**になっているか(抽象的な体験語ではなく、具体的な業務動作の言葉か)。

## Phase 3 — Apple的な洗練を重ねる(触りたくなる操作感)

見た目の秩序だけでは「触りたい」UIにならない。**触りたさ = 操作できる手掛かり × 結果の予測可能性 × 即応性 × 可逆性 × 操作による効果**という設計モデルで、操作感そのものを診断する。Appleの Fluid Interfaces / Human Interface Guidelines が繰り返し重視する軸で確認する。

- [ ] **操作可能性が形と状態で伝わるか**: 押せる・選べる・ドラッグできる・スクロールできる、をユーザーが試す前に見た目から判断できるか(hover/focus/pressed/selected の各状態を個別に設計したか)。
- [ ] **結果が予測できるか**: 同じ見た目の要素は、画面のどこにあっても同じ結果を返すか。同じ操作が場所によって違う挙動をしていないか。
- [ ] **反応が即座か**: 操作した瞬間(完了後ではなく開始した瞬間)に何らかの反応が返るか。時間のかかる処理は、何が起きているかを対象の近くで見せているか。
- [ ] **操作を止めたり戻したりできるか**: 操作の途中で中断・キャンセル・方向転換ができるか。誤操作からの復帰(Undo・取り消し・確定前のキャンセル)が用意されているか。
- [ ] **一手の効果が大きいか**: 1回の操作(フィルタ・一括変更・インライン編集)がまとまった仕事を進めるか。それとも、1件処理するたびに複数ページを往復させていないか。

上の5項目が触りたさモデルの本体。以下の2項目はその派生・補足チェックである。

- [ ] **(派生)動きは意味を運んでいるか**: アニメーションは状態変化・位置関係・因果を伝えるためだけに使われているか。装飾のための跳ねる・浮く・フェードするが、理由なく画面全体で反復されていないか。装飾のための動きだけをオフにしても機能が失われないか。
- [ ] **(派生)処理中も他の作業を止めていないか**: ある対象の処理待ちが、画面全体をブロックしていないか。処理は対象の近くに閉じ込められているか。

## Phase 4 — 装飾除去テストで検証する

- [ ] 色・カード・影・角丸を**すべて外して**この画面を見たとき、何が重要で、どこから見ればよいかが、配置・余白・順序・サイズだけで伝わるか。
- [ ] 画面をぼかして(あるいは縮小して)見たとき、**主作業領域が一つに見えるか**。
- [ ] この画面が何をするための画面か、**30秒以内に説明できるか**。
- [ ] 選択中・編集中・保存中・失敗・権限不足といった**通常状態以外**が、通常状態と同じ精度で設計されているか(存在するだけで満足していないか)。
- [ ] 一つでも崩れる項目があれば、**それは装飾によって整理されているように見せているだけ**。Phase 1〜2に戻って構造から作り直す。

## Phaseを通した進め方

1. 新規画面・リニューアルの着手時は、Phase 1の問いから**必ず**始める。既存画面を参考にする場合も、参考先の構造をそのまま輸入せず、この画面の業務構造で問い直す。
2. Phase 2〜3は並行して検討してよいが、**Phase 1の答え(中心対象・最頻操作)を先に確定させる**。対象が定まらないまま装飾の判断をしても、判断の軸がない。
3. 実装が一区切りついたら、Phase 4で必ず検証する。崩れた場合は装飾の調整では直らないため、Phase 1〜2に戻る。
4. 各チェックボックスの答えは、実装判断の根拠として**1行で残す**(なぜその構造にしたか、後から本人も含めて説明できるように)。

## 他スキルとの関係

- **Skill `ux-design`**: 本スキルで決めた「一手で終わらせる操作」「即応性」「可逆性」を、下書き保存・一括操作・エラー回復などの具体的な行動科学パターンとして実装する。
- **Skill `jp-web-design`**: 本スキルで決めた「何を主役にし何を隠すか」を、具体的な色・余白・タイポグラフィのトークンに落とし込む。
- 3つの関係: **design-judgment(何を作るか判断する) → ux-design(操作の仕組みを設計する) → jp-web-design(見た目のトークンに落とす)**。この順で通すと、装飾から入って崩れることがない。
- Phase 3の操作感チェックは「気づきのトリガー」(操作感の有無に気づくための問い)に過ぎない。摩擦の非対称性・一括操作・ドハティの閾値など、具体的な設計基準や行動科学用語の最終権威は `ux-design` とする。両者の記述が重複・矛盾する場合は `ux-design` を優先する。
