## 1. 収支表の現状構造（読み取り結果）

ブックは「月次収支表 × 12ヶ月（6月〜5月）」「年間集計（2024・2025）」「対前年（全体／粗利）」「項目説明」で構成されている。月次シートは車両1行 × 約101台、車両情報〜運行費・燃料費・修繕費・人件費・保険料・賦課税・運送費・管理費〜固定費/変動費/損益/利益率まで51列。

項目説明シートから、データの発生源はすでにかなり明確に整理されている。

| データ | 現在のソース | 性質 |
| --- | --- | --- |
| 稼働日数・稼働Km・燃費 | デジタコ → 車楽に連携 | 自動連携済み |
| 売上（運賃・附帯） | 車楽の車番別売上データ | システム内にある |
| 道路使用料 | デジタコETC → 車楽連携 | 自動連携済み |
| 高速割引料 | 組合割引率 0.356 で概算 | 推計ロジック |
| 軽油代（インタンク/外部） | 車楽に手入力＋燃料集計Excel（別担当が作成） | **手動リレーの起点** |
| 給与・賞与・福利厚生 | 車楽に手入力（賞与は年40万÷12の固定、福利厚生は社保合計） | 手動＋固定ロジック |
| 修繕費（車検・タイヤ） | 自社原価計算シートから km×単価（大型10.7円/km 等）で推計。ただし修理費列には実費も混在 | 推計と実費の混在 |
| 保険・税 | 車楽の車両マスタ一括配賦 | マスタ更新のみ |
| 一般管理費 | 売上 × 16.9%（3期平均）の一律配賦 | 固定率配賦 |

つまり「1次ソースはほぼ存在しており、人間がExcelにリレー転記して1枚にこしらえている」というヒアリングでの認識は、項目説明シートの記載とデータの中身から裏付けが取れた。

| 単価・効率型 | 車番203/73/217/3000/700 など（km単価128〜168円で赤字） | 稼働km単価の中央値は169円/km。中央値未満で走っている車は「仕事の単価が安いか運行効率が悪い」。営業・配車の課題 |
| 遊休・低稼働型 | 車番77・205・303・997・1327 など売上ゼロ〜30万未満が9台 | 固定費（保険・税・リース）だけ垂れ流し。5月だけで約▲59万円。保有台数・代替車の意思決定材料 |

さらに損益分岐の目安も出せる。1日あたり・1台あたりの原価は対前年シートで既に計算されており、1キロ原価 約173円／1キロ売上 約174円（4月）とほぼ差がない。**「km単価170円を割る仕事は構造的に赤字」という単純なKPIが、このデータからそのまま導出できる**（ヒアリングで話していた「損益分岐点から売上目標を逆算する」がすぐ実現可能な粒度でデータが揃っている）。

## 3. データ品質・業務プロセス上の課題

分析の信頼性に直結する問題が複数確認できた。

**(1) 入力ミス・未入力が毎月混入する。** ブック内の「5月入力確認」シートに既に12件の疑義（燃料未入力、修理費の桁疑い、人件費ゼロ等）が挙がっている。車番58は5月だけ燃料ゼロ、車番205は稼働しているのに人件費ゼロ、など。手動リレーである限りこのチェック工数は毎月発生する。

**(2) 月次集計への転記漏れ。** 「2025」年間集計シートの5月行が全てゼロのまま（5月収支表は完成しているのに反映されていない）。集計・対前年シートも手動転記に依存している証拠で、リレーの末端で数字が止まる。

**(3) 推計と実費の混在で「なぜ赤字か」が曖昧になる。** 修繕費は km×単価の標準原価と実費修理が同じブロックに入り、一般管理費は売上×16.9%の一律配賦。高売上車ほど管理費を多く背負う設計のため、車両単体の損益が「実力」を表さないケースがある（例: 車番800の▲140万のうちどこまでが実費でどこまでが配賦か、表からは追えない）。

**(4) 分析が属人化している。** 入力は山本氏、深掘り分析は今西氏が担い、今西氏のリソースが分析作業でパンクしつつある。表の右端の黒字/赤字を見て「売上が少ない・効率が悪い」で議論が終わる、というヒアリング内容はデータ構造からも妥当（原因分解の列がない）。

## 4. 改善の定義

ゴールは「**車両収支がクラウドで、入力最小・分析自動で回る状態**」。3つの軸で定義する。

### 軸A: 入力の自動化（山本氏の工数削減）

入力項目を「①1次ソースから自動で決まるもの／②運転者・車番が決まれば連鎖して決まるもの／③毎月人間が入れるしかないもの」の3層に棚卸しし、③を5項目以内に絞り込むことを目標とする。

現時点の見立てでは、デジタコ・ETC・車楽売上は既に連携済みなので自動化可能。燃料は「燃料集計Excelを作っている担当」の1次ソース（給油サイト・インタンク記録）まで遡って自動取込にする。給与は給与計算の大元から総支給額だけ取れれば、賞与（固定）・福利厚生（社保連動）は自動計算に落とせる。保険・税・リースはマスタ配賦のままでよい（更新イベント時のみ入力）。タコメーター出力がPDFならOCR自動入力、テキスト/Excelならコピペで自動生成、という取込UIを用意する。

成果指標: 収支表作成の月次工数（現状: 要ヒアリングで計測）を7〜8割削減。入力ミス起因の手戻りゼロ。

### 軸B: 分析の自動化（今西氏の工数削減と意思決定の質向上)

人間が表を眺めて気づく作業を、登録と同時に自動で出す。

第一段はAI不要の統計処理だけで成立する: 外れ値・未入力の自動検知（「5月入力確認」シートで手動/半手動でやっていることの完全自動化）、km単価170円ラインでの赤字予備軍フラグ、赤字を「突発修繕型／単価・効率型／遊休型」に自動分類、修繕費の月次一括計上を12ヶ月按分した実力損益の併記、車種・拠点・運転者で標準化した比較（同条件で並べて「この車だけ売上が低い→営業案件」を特定）。

第二段でClaudeに解釈とサジェストをさせる: 「今月の赤字車39台のうち、営業単価の見直しが必要なのは◯台・◯◯円分」「損益分岐から逆算した来月の車両別売上目標」といった経営者・管理者向けレポートを月次自動生成。最終判断は人間。

成果指標: 月次の分析レポート作成が自動化され、今西氏は「判断」だけに時間を使う状態。

### 軸C: クラウド化とエコシステム（横展開の土台）

CloudflareのDBに車両・運行・経費データをネイティブに蓄積し、Excelアップロード不要でClaudeが直接参照できる状態にする（Claude Platformの標準構成）。周辺として、Kintone MCPカスタムコネクタを初月に検証し、Kintone上のデータ・チャットの取込可否を判定する。現場UIは「AIらしさ」を出さず、Slack（またはKintone）で"こいつに聞け"の窓口を作り、見積・資料は裏側でClaudeが生成→管理者にメンション、というフローを組む。

このモデルケースは運送業界に横展開可能（商工中金の車両収支ツールとの差別化＝「繋がっていて、解釈までする」）であり、TierMind側の裏目的とも一致する。

## 6. 初回に確認・決定が必要なこと

進める前に顧客側と握るべき点は次の5つ。①燃料集計Excelの1次ソース（どのサイト/機器から誰がどう取っているか）。②給与データの大元（給与計算ソフト名と出力形式）。③車楽からのデータ出力手段（CSV出力/API/画面のみか）。④修繕費の「推計」と「実費」をDB上で分けて持つことの合意（実力損益を出すため）。⑤一般管理費16.9%配賦の扱い（当面現行踏襲か、配賦基準の見直しまで踏み込むか）。
