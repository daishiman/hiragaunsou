# デザインシステム — 信頼のためのミニマル設計

どのアプリにもそのまま移植できる、日本企業向けの「静かで信頼できる」デザインの土台。
装飾を足して良く見せるのではなく、**まず余白・整列・文字の強弱**で秩序を作る。罫線・色・アイコン・画像は、無いと意味や操作を誤る場合だけ使う。

> このドキュメントは規範（守るべきルール）です。迷ったら「色を足す」ではなく「余白と階層で解く」を選ぶ。

## 適用境界と上流SSOT

この文書が決めるのは、定まった情報設計を**どう表示するか**だけ。画面の目的や必要情報を、見た目の都合で変更しない。

| 決めること | 上流SSOT | この文書との境界 |
|---|---|---|
| 誰が、どの場面で、何件を扱い、何を終えるか | `docs/product/T2-experience-spec.md` | カード/表などの骨格、情報の優先順、表示用加工はT2から導く |
| 画面の名前、所属、並び、兄弟画面との違い、次の行き先 | `docs/product/T6-information-architecture.md` | ナビゲーションと画面の意味契約はT6を正とする |
| 色、文字、余白、罫線、部品、フォーカス、印刷の表示文法 | **本文書** | T2/T6の決定を、全画面で同じ見え方にする |

T2/T6と本文書が衝突したらT2/T6を優先する。ただし、キーボード操作、読み上げ、コントラスト等のアクセシビリティ要件は見た目の好みで外さない。

## 0. 5秒でわかる原則

1. **色数を絞る** — 画面の90%は白・グレー・黒の文字。色は操作と結果にだけ。
2. **黒背景パネルを作らない** — 強調は色ではなく、余白・罫線・文字サイズで。
3. **折返しを設計する** — 単語・数字・チップの「途中折返し」「1個だけ折返し」を禁止する。
4. **動きは因果の説明だけ** — 装飾のためのアニメーションを足さない。`reduced-motion`で全部止まる。
5. **数字はすべて本物** — 演出のための偽の数字・煽り・偽の緊急性を使わない。

この5つを破らなければ、たいていのUIは「信頼できる」見え方になる。

## 1. カラー — 60-30-10（最重要）

| 比率 | 役割 | 使う色 |
|---|---|---|
| **60%** | 地・背景・カード | 白 / 極薄グレー |
| **30%** | 文字・罫線・区切り | 黒に近いグレー / 薄いグレー罫線 |
| **10%** | 操作と結果 | ブランド青（操作）+ アクセント（CTAとキー数字だけ） |

### ルール（禁則）

- **ブランド（青系）**は「操作・選択状態・リンク・進捗」**のみ**。装飾に使わない。
- **アクセント（オレンジ系）**は **主要CTAボタン + 結果のキー数字の2箇所だけ**。3箇所目が欲しくなったら設計が間違っている。
- 緑=成功・黄=注意などのステータス色を「彩り」として増やさない。**1画面の色相は3つまで**。
- **黒・ダーク背景のパネルは禁止**（ヒーロー/結果カードを黒地にしない）。
- 絵文字・素人っぽい自作SVGアイコンは使わない。装飾や説明は番号（01/02/03）とタイポグラフィで構成する。
  操作ボタンに限り、`app/_components/Icon.tsx` の規格化された最小セットだけ使ってよい（判断基準は §11-10）。

### トークン（実績のある初期値）

```css
:root {
  /* 操作・選択・リンク・進捗 */
  --brand: #1d63be;        /* blue-600 */
  --brand-deep: #15498f;
  --brand-soft: #eef4fc;

  /* CTA + キー数字だけ（この2用途以外に使わない） */
  --accent: #e8590c;
  --accent-deep: #c74e0b;

  /* テキストと構造（画面の90%） */
  --ink: #16191d;          /* 本文 */
  --ink-muted: #545e6b;    /* 補足・ラベル */
  --line: #e3e6ea;         /* 罫線・境界 */
  --subtle: #f5f6f8;       /* 極薄の面 */

  /* 意味を持つ状態色（彩りではなく機能） */
  --danger: #d93025;       /* エラーのみ */
  --caution-soft: #fdf6e3; /* 注意の面 */
  --caution-border: #e6c96a;
}

body {
  /* 白カードを立たせるための極薄グレー地（60-30-10の「60」） */
  background: #f6f7f9;
  color: var(--ink);
  font-feature-settings: "palt"; /* 日本語の詰め */
}
```

ブランドを別の色に振り替えるとき（企業カラー適用）も、**役割の割り当て（操作=1色 / CTA・キー数字=1色）は変えない**。色相の数だけを守れば信頼感は保たれる。

## 2. タイポグラフィと日本語組版

### スケール（用途ベース・むやみに種類を増やさない）

| 用途 | サイズ | 太さ |
|---|---|---|
| ページ主数字（結果） | `text-4xl`〜`5xl` | bold・アクセント色 |
| セクション見出し | `text-sm font-bold` | 太字・inkだが小さく |
| 本文 | `text-sm` | normal |
| 補足・ラベル | `text-xs text-ink-muted` | normal |

> 見出しを「大きく・色付き」にして目立たせない。日本企業のUIでは**見出しは小さく静かに**、主役は中身（数字・事実）。

### 折返し・整列の禁則

- 見出しは `text-wrap: balance`。分断しやすい語は**文節単位で** `<span class="inline-block">評価</span>` にして「評/価」の分割を防ぐ。
- **数値は必ず** `tabular-nums` + `whitespace-nowrap`（下の `.tnum`）。「3億7,116万/円」の途中折返しは禁止。
- 狭い場所では概数に切り替える：「2億3,048万円」→「約2.3億円」。
- **チップ・ボタン群の「1個だけ折返し（孤児）」を禁止**。flex-wrapの成り行きに任せず等幅グリッドで：
  - 4個 = `grid-cols-2 sm:grid-cols-4` / 5個 = `grid-cols-3 sm:grid-cols-5` / 6個 = `grid-cols-3 sm:grid-cols-6`
  - 2択は `grid-cols-2` で横幅いっぱい等幅（3列に置いて左に寄せない）。
- ラベルは列幅に収まる短さに書き直す（「330㎡以内（約100坪）」→「330㎡以内」、補足は説明文へ）。
- JSX内の改行はスペースになる。日本語の連続文は `{'…'}` で1つの文字列にする。

```css
.tnum {
  font-variant-numeric: tabular-nums;
  white-space: nowrap;
}
```

### 表示用の値と正確値の二層

DBの値を人が理解しやすい表記にするか、原本と突合できる正確値で出すかは、画面の主目的で分ける。

| 主目的 | 主表示 | 要件 |
|---|---|---|
| 読む・判断する | 年齢、業務状態語、3桁区切り、「1週間前」などの表示用の値 | 正確値へ詳細、ツールチップ、`datetime`、原本リンク等で戻れること |
| 入力・突合・監査・印刷・出力 | 正確な金額、日時、コード、原本の値 | 丸め値や相対日時だけを出さない。補助表示を付けても正確値を主とする |

- 表示用加工は `app/_lib/format.ts` 等の共通formatterに寄せ、画面のJSXごとに書かない。
- formatterは表示を変えるだけで、保存値や監査原本を書き換えない。
- 相対日時は会話や直近状態の把握にだけ使う。監査台帳と `/grid/report` は正確日時を出す。

## 3. レイアウトと間隔

- **面の重ね方**：極薄グレー地（`#f6f7f9`）の上で、独立して操作・選択する単位だけを**白カード**（`bg-white border border-line`）にする。同じ判断に使う情報群は余白と整列でまとめ、群ごとに箱を増やさない。
- **角丸**：カード `rounded-xl` / コントロール・小要素 `rounded-md`。混在させず用途で固定する。
- **内側余白**：カード `p-5` / 行 `px-4 py-3` を基準に。詰めすぎない。
- **区切り**：行の追跡を誤る列挙だけ、`border-b border-line` の細罫線で分ける（最後の行は `last:border-b-0`）。短い列挙は余白だけで分かるかを先に試す。
- **定義リスト**：`grid grid-cols-[8rem_1fr]` でラベル列を固定幅に。値は左揃えで縦のラインを通す。

影（`shadow`）はモーダルなど「浮いている」ことに意味がある要素だけ。通常のカードに影を付けない。

### ラベル・線・アイコン・画像の採否

要素を足すか削るかは「無いと何を誤読するか」で決める。見た目を賑やかにすることは採用理由にならない。

| 要素 | 使うとき | 使わないとき | 必須条件 |
|---|---|---|---|
| ラベル | 値だけで意味が一意にならない、入力欄、表の列見出し | 名称・住所・金額など書式と配置で意味が明白な読取り専用値 | 値より小さく静かにする。視覚的に省いても支援技術用の名前は残す |
| 線 | 余白と整列だけでは隣接行や操作範囲を誤読する | グループごとの箱、格子、彩り目的の罫線 | 最小の1本とし、先に群間の余白を群内の2〜3倍にできないか試す |
| アイコン | 閉じる・開閉・メニューなど、押す前の結果が一意に分かる操作 | 業務語や「それらしさ」を表す飾り | `IconButton` / `Icon.tsx` を使い、動作を示す `aria-label` とフォーカス時も出るツールチップを持つ |
| 画像 | 対象の識別、原本の証拠、文章より早い構造説明のいずれか | 金額・状態・操作の説明に寄与しない飾り | 用途と代替テキストを定義し、375/768/1280/1600pxで確認する |

**画像の用途別ルール**

- **識別**：文字より画像が対象を見つける主な手がかりのときだけ、一覧の第一階層に置く。サムネイルは同じ比率にそろえ、識別対象が欠けない範囲でだけトリミングしてよい。
- **証拠**：伝票、請求書、取込原本はトリミングしない。`object-fit: contain` 相当で全体を見せ、原寸/原ファイルへの導線と、ファイル名・対象月・取込日時などのキャプションを残す。
- **説明**：画像が伝える関係を `alt` に書く。キャプションに同じ説明があるときは二重に読み上げない。
- **装飾**：情報を持たない画像は置かない。やむを得ず使う背景装飾は `alt=""` とし、読み上げと操作順から外す。

### 高密度の表を「表のまま」読みやすくする

同じ項目を大量に入力・突合・監査するときは表が正しい。カードに置き換えるのではなく、表の中に階層を作る。

- 識別のキー列（例：車番）は左端に置き、横スクロール中も対象を見失わないよう固定を検討する。
- 列はT2の優先順で左から並べ、同時に使う列をグループ見出しと余白で束ねる。
- 金額は右揃え + `tabular-nums` + 正確値。異常・未反映・変更中のセルだけを文字と形で強調する。
- 格子罫線とゼブラで埋めない。列見出し、最小の行境界、hover/focus、固定列の境界だけを使う。
- 表の外に「何を見ればよいか」と説明文を足す前に、列順、列見出し、例外の強調、次の操作を直す。
- 幅が狭いときも、大量突合という主目的が同じなら安易にカード化しない。主要項目だけを読む別の主目的に切り替えるときだけ、リスト/カードにする。

## 4. コンポーネント（コピペで移植できる最小セット）

すべて上のトークン前提。Tailwindのクラス名は役割どおりに読める。

### ボタン

```html
<!-- 主要CTA（画面に基本1つ。アクセント色はこことキー数字だけ） -->
<button class="pressable rounded-md bg-accent px-5 py-2 text-sm font-semibold text-white
               hover:bg-accent-deep disabled:opacity-50">送信する</button>

<!-- セカンダリ（操作=ブランド色の罫線ボタン） -->
<button class="pressable rounded-md border border-brand px-4 py-2 text-sm font-semibold
               text-brand-deep hover:bg-brand-soft disabled:opacity-50">編集</button>

<!-- 三次（静かな操作） -->
<button class="pressable rounded-md border border-line bg-white px-4 py-2 text-sm
               text-ink hover:bg-subtle">キャンセル</button>
```

- ラベルは**動詞で終える**（「送信する」「保存する」）。「〜させていただく」禁止。
- `.pressable` で押下フィードバック（`active:scale(0.98)`）。

### カード

このアプリ内では **`.card` クラス**（`app/globals.css`）を使う。角丸・罫線・白背景・`min-width:0` が
1箇所にまとまっており、`rounded-xl border border-line bg-white` と書き並べるのは禁止
（見た目は同じでも、はみ出し対策の `min-width:0` が抜けるため）。

```html
<section class="card p-5">
```

移植先で `.card` が無い場合の等価な素の指定：

```html
<section class="rounded-xl border border-line bg-white p-5">
  <div class="mb-4 flex items-baseline justify-between gap-3">
    <h2 class="text-sm font-bold text-ink">セクション見出し</h2>
    <!-- 右肩の補助操作/件数など -->
  </div>
  <!-- 中身 -->
</section>
```

### 定義行（ラベル + 値）

```html
<div class="grid grid-cols-[8rem_1fr] items-baseline gap-2 border-b border-line py-2 text-sm last:border-b-0">
  <dt class="text-xs text-ink-muted">評価額</dt>
  <dd class="text-ink"><span class="tnum">2,300万円</span></dd>
</div>
```

### ステータスバッジ（色相を増やさず塗り/罫線で区別）

状態を色で塗り分けたくなるが我慢する。**塗り・罫線・打消し線の違い**で区別すると色相が増えない。

```html
<span class="inline-flex items-center whitespace-nowrap rounded-full border px-2.5 py-0.5 text-xs font-medium bg-brand-soft text-brand-deep border-transparent">進行中</span>
<span class="... bg-subtle text-ink border-line">成約</span>
<span class="... bg-subtle text-ink-muted border-line line-through decoration-1">売却済</span>
<span class="... bg-white text-ink-muted border-line border-dashed">取下げ</span>
```

### 空状態（EmptyState）

```html
<div class="rounded-lg border border-dashed border-line px-6 py-12 text-center">
  <p class="text-sm font-semibold text-ink">まだ登録がありません</p>
  <p class="mt-1 text-sm text-ink-muted">最初の1件を追加すると、ここに一覧が表示されます。</p>
  <div class="mt-4"><!-- 主要アクション --></div>
</div>
```

### スケルトン（読み込み中）

```html
<div class="skeleton h-10 w-full"></div>
```

### 注意の面（機能としての色）

```html
<div class="rounded-md border border-caution-border bg-caution-soft px-4 py-3 text-xs leading-relaxed">
  この操作は取り消せません。内容をご確認ください。
</div>
```

## 5. モーション（控えめ・因果の説明のみ）

すべて `prefers-reduced-motion: reduce` で無効化する。装飾のための動きは足さない。

| 用途 | 実装 | 時間 |
|---|---|---|
| 画面/質問の遷移 | 方向つきスライド（`--dir: 1/-1` で進む/戻る） | 出150ms / 入260ms |
| カード・選択肢の入場 | `rise-in`（fade + translateY(10px)）+ `--stagger` で1枚40〜70ms刻み | 260ms |
| 選択フィードバック | チェックの `pop-in`（scale 0.4→1） | 180ms |
| 押下 | `.pressable`（`active:scale(0.98)`） | 100ms |
| 進捗・数値 | バーの width transition / カウントアップ（rAF + ease-out） | 300〜900ms |

```css
@keyframes rise-in { from { opacity:0; transform: translateY(10px); } to { opacity:1; transform: translateY(0); } }
.rise-in { animation: rise-in 260ms cubic-bezier(0.2,0,0,1) both; animation-delay: var(--stagger, 0ms); }

@keyframes pop-in { from { opacity:0; transform: scale(0.4); } to { opacity:1; transform: scale(1); } }
.pop-in { animation: pop-in 180ms cubic-bezier(0.2,0,0,1) both; }

.pressable { transition: transform 100ms; }
.pressable:active { transform: scale(0.98); }

@keyframes pulse-soft { 0%,100% { opacity:1; } 50% { opacity:.45; } }
.skeleton { background: var(--subtle); border-radius: 6px; animation: pulse-soft 1.4s ease-in-out infinite; }

@media (prefers-reduced-motion: reduce) {
  .rise-in, .pop-in, .skeleton { animation: none; }
  .pressable, .pressable:active { transition: none; transform: none; }
}
```

選択 → 自動送りは「ハイライトを一拍（約160ms）見せてから」遷移する。

## 6. アクセシビリティ

- **キーボードフォーカスを必ず可視化**（`:focus-visible` に2pxのブランド色アウトライン）。
- コントラスト：本文は `--ink`、補足は `--ink-muted` まで。それより薄いグレーを本文に使わない。
- タップ領域は最低44px相当を確保。
- 装飾要素（スケルトン等）は `aria-hidden`。
- 状態を色だけで伝えない（バッジは文字ラベルも持つ）。

```css
:where(a, button, input, select, textarea, summary):focus-visible {
  outline: 2px solid var(--brand);
  outline-offset: 2px;
  border-radius: 4px;
}
```

## 7. 結果・レポート画面の情報階層

**白・余白・罫線で階層を作る。カードの色分け・背景色に頼らない。**

1. **主数字** — 小さいグレーのラベル + 大きな数字（ページで唯一のアクセント色）。装飾なしで中央に。
2. **前提ストリップ** — 上下の細罫線だけの3カラム（脇役として静かに）。
3. **事実カード** — ユーザーが次に知りたいこと（実際の額・期限）を白カードで。
4. **比較バー** — 現状（グレー）vs 改善後（ブランド色）。**バーには必ずラベルと数値を付ける**（裸の棒は意味不明）。
5. **CTA**（アクセント色・全幅）。
6. **根拠の開示**（折りたたみ）+ 免責。

各ブロックは `rise-in` + stagger で上から順に現れる。

## 8. UXライティング

- 比喩・話し言葉・キャッチーな造語を避け、**誰が読んでも同じ意味になる直接表現**にする。
- 専門用語は生活の言葉に言い換える（内部計算では正確な用語を使う）。
- ボタンは動詞で終える。1文50字以内。「〜させていただく」禁止。
- **表示する数字はすべて実際の計算結果**。偽の緊急性・煽り・confirmshaming（罪悪感を煽る選択肢）禁止。

## 9. 新規アプリへの導入手順（Tailwind v4）

1. `globals.css` の先頭に `@import "tailwindcss";` を置く。
2. 上の **§1 のトークン**（`:root`）と **§5・§6 のCSS**（`.rise-in` / `.pop-in` / `.pressable` / `.skeleton` / `.tnum` / `:focus-visible`）をコピーする。
3. トークンをTailwindのユーティリティとして使えるよう `@theme inline` に橋渡しする：

```css
@theme inline {
  --color-brand: var(--brand);
  --color-brand-deep: var(--brand-deep);
  --color-brand-soft: var(--brand-soft);
  --color-accent: var(--accent);
  --color-accent-deep: var(--accent-deep);
  --color-ink: var(--ink);
  --color-ink-muted: var(--ink-muted);
  --color-line: var(--line);
  --color-subtle: var(--subtle);
  --color-danger: var(--danger);
  --color-caution-soft: var(--caution-soft);
  --color-caution-border: var(--caution-border);
}
```

4. 企業カラーを当てる場合は `--brand` / `--accent` の**値だけ**差し替える。役割（操作=1色 / CTA・キー数字=1色）は変えない。
5. §4のコンポーネントをそのまま貼って肉付けする。

## 11. 共通部品カタログ（このアプリの実装規約）

**大原則: 画面ごとに直さない。** 見た目・言い回し・折り返しの指定は下の部品と
`app/_lib/screens.ts` の1箇所だけが持つ。ページ側は「定義を1行足して、部品を呼ぶ」だけにする。
同じマークアップやクラス指定をページにコピペで並べた時点で、次の改善が画面数ぶんの手間になる。

### 11-1. T6の実行用定義: `app/_lib/screens.ts`

T6で決めた画面の **名前・所属グループ・並び順・リード文・工程順・「ここでは見ないこと」「次にどこへ」** を
実行時に使う形で1ファイルに集約している。画面の骨格と情報の優先順を新しく決める文書ではない。ここから下記がすべて導出される。

| 導出先 | 実装 |
|---|---|
| サイドバーのグループと並び | `app/_lib/navigation.ts`（`SCREENS` を詰め替えるだけの薄い層） |
| ページ見出し・種別バッジ・役割ノート | `app/_components/ScreenHeader.tsx` |
| 毎月の締めの「n / 5」と前後リンク | `flowPositionOf()` |
| 権限によるメニューの出し分け | `visibleScreens(role)` |

- **使うとき**: 画面を追加した／名前を変えたい／並びを変えたい／説明文を直したいとき。
- **使ってはいけない場合**: 無い。画面の名前と説明をここ以外（ページのJSXやサイドバー）に書くのは禁止。
- 定義漏れは「文言が出ない」という無言の不具合になるため、`tests/lib/screens.test.ts` で
  全画面が `label / title / lead / does` を持つこと、定義された `notHere / next` のリンク先が実在することを固定している。`notHere / next` はT6 §3の条件に合う画面だけが持つ。

### 11-2. `ScreenHeader`（通常画面のページヘッダ）

```tsx
<ScreenHeader screen="/cleansing" action={<MonthPicker />} help={<SourceDataNote />} />
```

見出し・リード文・種別バッジ・工程上の位置と前後リンクを、`screens.ts` の定義から描く。
役割ノートは `does` を必ず持ち、`notHere` / `next` は定義されているときだけ行を出す。「3行分の枠を先に出す」「空の説明を埋める」はしない。

- **使うとき**: 通常の操作・閲覧画面。ページの先頭に1つ。
- **例外**: 印刷・帳票の `/grid/report`。文書見出し、対象月、出力時点、戻る/印刷操作を印刷レイアウトの先頭に持つため `ScreenHeader` を重ねない。
- **`title` / `lead` を上書きしてよい場合**: 対象月・車番・件数など**実データを含む見出し**のときだけ
  （例: `title={\`車番 ${no}\`}`）。言い回しを変えたいだけなら `screens.ts` を直す。
- **使ってはいけない場合**: ページから `PageHead` を直接呼ぶこと。`PageHead` は `ScreenHeader` 専用の下地。

### 11-3. `Card` / `.card`（囲みの面）

```tsx
<Card title="利用者別内訳">…</Card>       // 見出し付き
<section className="card p-5">…</section>  // 見出し不要・レイアウトを自分で組むとき
```

- **使うとき**: 白い面で囲むものすべて。
- **使ってはいけない場合**: `rounded-xl border border-line bg-white` と直接書くこと。
  `.card` は角丸・罫線・背景に加えて **`min-width: 0`** を持つ。これが無いと、
  横に並べた要素の中で長い日本語が縮まず、枠からはみ出す。
- `padding="tight"` は表を端まで見せたいとき（内側で余白を持つ場合）だけ。

### 11-4. `Prose` / `.prose-note`（長い文章を入れる器）

```tsx
<Prose>ここに数行の日本語を書いても、カードの外へは出ない。</Prose>
```

折り返し規則（`overflow-wrap: anywhere` / `word-break: auto-phrase` / `line-break: strict`）を
持つのは `globals.css` の `.prose-note` **1箇所だけ**。

- **使うとき**: 説明文・注意書き・URLやファイル名を含む文など、1行に収まらない可能性のある文章。
- **使ってはいけない場合**: 数値・金額（`num` を使う。途中で折り返してはいけない）、
  表のセル（列幅で制御する）。

### 11-5. `Disclosure`（折りたたみ）/ `Drawer`（引き出し）

- **`Disclosure`**: その場で読みながら操作を続ける説明（「どのファイルを選べばよいですか?」など）。
  本文は自動で `prose-note` に入るので、長い説明を書いてよい。
- **`Drawer`**: 読み終わったら画面から消えてよい長い説明。
- **使ってはいけない場合**: どちらも「隠すと業務が止まる情報」には使わない（必須の入力条件・エラー理由）。

### 11-6. `StagePanel` / `AlertPanel` / `EmptyState` / `StepRail`

| 部品 | 使うとき | 使ってはいけない場合 |
|---|---|---|
| `StagePanel` | 作業を段階に区切って見せるとき（取込・整形） | 単なる見出し付きの囲み（→ `Card`） |
| `AlertPanel` | 手を止めて読む必要がある注意・警告 | 常設の補足説明（→ `Prose`）。多用すると誰も読まなくなる |
| `EmptyState` | 一覧が0件・表が空のとき。**理由と次の一手を必ず書く** | 読み込み中（→ スケルトン） |
| `StepRail` | 工程の現在地を画面内に出すとき | 工程外の画面（`ScreenHeader` が工程番号を出さないのと同じ理由） |

### 11-7. はみ出しの根治（`globals.css`）

flex / grid の子要素は既定が `min-width: auto` で、**中の一番長い塊より小さくならない**。
日本語の長い一文や英数字の羅列があると、そこで枠を押し広げてはみ出す。
そのため画面ごとにパッチを当てず、`globals.css` で以下をまとめて効かせている。

- `main` 配下の面（`section` / `div` / `dl` / `details` など）に `min-width: 0`
- 画像・埋め込み・`pre`・入力欄に `max-width: 100%`
- `.card` とその直下に `min-width: 0`、`.prose-note` に `min-width: 0` / `max-width: 100%`

**`table` に `max-width: 100%` を掛けてはいけない。** 収支表などの横長の表は、外側の枠
（`overflow-x-auto`）より広いままにして横スクロールさせる作りになっており（`min-w-full` /
`min-w-[36rem]` / セルごとの `min-w-*`）、上限を掛けると列が潰れて読めなくなる。
同じ理由で `.card > *` にも上限を掛けない（カードの直下には表の外枠が入るため）。

いずれも `:where()` で書いており詳細度は0。Tailwind の `min-w-full` などを個別に当てれば勝てるので、
表を横スクロールさせたい箇所は今まで通り書ける。

### 11-8. `editForm`（まとめて保存する画面の作法）

値を打ち替えて保存する画面（率マスタ設定・車両マスタ管理・運転者マスタ管理・手入力）は、
`app/_components/editForm/` の一組で作る。画面ごとに保存や差分の判定を書かない。

```tsx
const FIELDS: EditableFieldDef<Driver>[] = [{ field, label, kind, read }]  // 何を編集できるかの宣言
const form = useEditableRecords({ records, rowKey, fields, submit })       // 変更の検知・未保存件数・取り消し
<EditableRowCells … /> / <EditFormActionBar form={form} />                 // 表示
```

| 決めごと | 実装 | 理由 |
|---|---|---|
| 保存の単位 | 画面ごとに1回。変更のあった項目だけ送る | 1欄ずつ即時保存だと収支表の作り直しが何十回も走り、途中でやめたとき「どこまで保存されたか」が分からない。全項目を送ると触っていない欄まで更新履歴に載る |
| 変更の判定 | 打鍵ではなく**読み取った値**で比較（`1,200` と `1200` は同じ） | 判定が甘いと「未保存◯件」が嘘になり、誰も見なくなる |
| 変更の見せ方 | `ChangedFieldMark`。背景/罫線（`--brand-soft` / `--brand-deep`）＋「変更」の札＋「元: ◯◯」の併記 | **色だけの区別は不可**。§6 のとおり色覚特性と読み上げの両方に対応する |
| 保存できないとき | ボタンを押せなくするだけでなく、**理由を必ず文字で帯に出す** | 押せない理由が分からない画面は問い合わせを生む |
| 一部だけ失敗 | 欄単位で返し、打った内容を残したまま赤く出す | 全体を失敗にすると直した10項目が全部消える |
| 離脱の引き止め | `UnsavedLeaveGuard` を置く | 画面ごとに `beforeunload` を書かない。`YearMonthSelect` は `requestLeave()` の戻り値（true＝移動した）に依存する |

**使ってはいけない場合**: 1件だけの登録フォーム（→ 素の form でよい）、押した瞬間に確定させたい操作（データ整形の「除外する」など判断ボタン）。

新しいマスタ項目を足すときは、画面のコードではなく `FIELDS` の宣言に1行足す。

### 11-9. サイドバーに出すか、アカウントメニューに入れるか

依頼者の指摘（2026-08-09）:

> サイドバーに情報が膨大にありすぎて認知負荷がかなり高い。
> 「絶対にこの情報がないと分からない」という情報だけを表示する形に整えてほしい。

画面を1枚足すとき、**サイドバーに常時出すか、ユーザー名から開くアカウントメニューに入れるか**は
`app/_lib/screens.ts` の `SCREEN_GROUPS` にある `placement` 1箇所で決まる。判断は次の順で行う。

**① 使う頻度で置き場所を決める**（憶測ではなく `docs/product/data-flow-map.md` の業務フローで判定する）

| 頻度 | 置き場所 | 例 |
|---|---|---|
| 毎月の締めで何度も行き来する | `placement: "sidebar"`（常時1クリック） | データ取込・データ整形・手入力・チェック・月次収支表 |
| 月に1回前後、締めの前後で使う | `placement: "sidebar"` | ダッシュボード・年間集計・3つのマスタ・直した内容の反映 |
| 月に1回も開かない（運用・設定・仕様書） | `placement: "account"`（+1クリック） | マイページ・ユーザー管理・AI設定・利用状況・取込データ管理・データ設計の説明 |

**②「これが無いと何が分からなくなるか」に答えられない常時表示は置かない**

サイドバーに何かを足したくなったら、この問いに1文で答える。答えられなければ出さない。

| 出すもの | 答え | 判定 |
|---|---|---|
| メニュー項目のラベル | どの画面があるかが分からなくなる | 出す |
| グループ見出し | どの画面が同じ目的の仲間かが分からなくなる | 出す（押せないラベルとして） |
| 未判定の件数バッジ | **画面を開くまで、まだ手が残っているかが分からない** | 出す |
| 登録済み台数のバッジ | 見ても次にやることが変わらない | 出さない（廃止済み） |
| グループを畳んだときの項目数 | 何も分からなくならない | 出さない（廃止済み） |
| 「まずはここ」のような案内バッジ | 位置と面の色ですでに伝わっている | 出さない（廃止済み） |

**③ 折りたたみは使わない。隠すならサイドバーごと隠す**

グループの折りたたみは廃止した。畳むと中の画面が2クリックになり、毎月の締めで何度も往復する
画面が遠くなる（削った情報量に対して払うクリックが割に合わない）。
「画面に集中したい」という要望には、ヘッダの `メニューを隠す` / `メニューを表示` で
**サイドバーごと** 隠す方法で応える。隠しても戻すボタンは同じ位置に出たままで、1操作で戻せる。

**④ どこに置いても、現在地は必ず分かるようにする**

- サイドバーの項目 → `aria-current="page"` と面の色。
- アカウントメニューの中の画面 → ユーザー名の下にロールの代わりに画面名を出し、トリガー自体を色づける。
- どちらの場合も、ヘッダには常に現在の画面名が出ている（隠していても迷子にならない）。

**⑤ 移した画面は必ず別の場所から辿れること**

サイドバーから外した画面は、到達不能になると「実装済みなのに誰も使えない」無言の不具合になる。
`tests/lib/navigation.test.ts` と `tests/components/AppShellAccountMenu.test.tsx` で、
**ロール別に、開ける画面がすべてサイドバーかアカウントメニューのどちらかから辿れること**を固定している。

**使ってはいけない場合**: 画面の名前・並び・置き場所を `AppShell.tsx` に直接書くこと。
すべて `screens.ts` から導出される（§11-1）。

### 11-10. アイコンにしてよい操作、文字を残す操作

依頼者の指摘（2026-08-09）:

> 「メニュー」っていうボタンがありますが、これって何のメニューボタンですか？押したところで何か表示されるわけでもないです。
> 視覚的にわかるように文字とボタンを配置していますが、これだと分かりにくかったり、逆に鬱陶しいところがある。
> 箇所によって「文章＋ボタン」がいいのか「アイコンのボタン」がいいのかは色々ありますが、いい塩梅で整えてほしい。

**① アイコンだけにしてよいのは「意味が一意に決まる操作」だけ**

| 操作 | 見せ方 | 理由 |
|---|---|---|
| メニューを隠す / 表示する | **アイコンのみ** | 開閉は形だけで通じる。文字にすると常時2文字以上が居座り、業務のボタンと同じ重さで見える |
| 閉じる（×） | **アイコンのみ** | 世の中の共通語彙 |
| 開閉の向き（∨ ∧） | **アイコンのみ** | ボタンの状態を示す補助。単独では押さない |
| 取り込む / ここまでを保存 / 確定する / 書き出す | **文字（動詞）** | 業務語。アイコンにすると意味が人によって変わり、押す前に確認が要る |
| 一覧に戻る / 次の工程へ | **文字（動詞）** | 行き先が名前でしか分からない |
| ？（この画面について） | **文字（?）** | すでに1文字。アイコンにしても減らない |

判断の一文: **「この形を初めて見た人が、押す前に何が起きるか言えるか？」** 言えないならアイコンにしない。

**② アイコンにするなら、意味に辿り着く道を2本残す**

`app/_components/IconButton.tsx` を使う。1箇所で次を必ず満たしている。

- `aria-label` … 読み上げとテストが「メニューを隠す」という**動作の名前**で特定できる
- ツールチップ … `useHoverTooltip` で **ホバーでもフォーカスでも**同じ文が出る（`aria-describedby` で結ぶ）

ラベルは**名詞ではなく動作**で書く。`メニュー` は禁止、`メニューを隠す` と書く。
状態が変われば名前も入れ替える（隠す ⇄ 表示する）。

**③ 図形は `app/_components/Icon.tsx` の表からしか使わない**

- 絵文字は禁止（§1 禁則）。**その場で `<svg>` を書き起こすことも禁止**（線幅も角丸もサイズも揃わない）。
- 形は Lucide と同じ幾何（24×24 / 線幅1.5 / 端は丸め / 塗りなし）に固定。世間で使われている形だけを採り、独自の比喩（電球・ロケット等）は描かない。
- 増やすときは `IconName` に1行足す。ここに無い形が要るということは、たいてい**文字で書くべき操作**である。

**使ってはいけない場合**: 装飾としてアイコンを添えること。アイコンは操作にだけ付ける。

### 11-11. 本文の幅（全画面いっぱい。狭めるのは箱ではなく行）

依頼者の指摘（2026-08-09、3度にわたる）:

> なぜ左側のスペースじゃなくて右側のスペースが空いているのが気になります。**全画面共通でお願いします。**（`/import`）
> このページも右側に空白が空いています。**全てのページ見直して改善を行ってください。**（`/report`）
> これらも（`/profile`・`/ai-settings`）
> **今後、同様に新しく画面追加した場合でも、これを対応できるようにしておいてほしいです。**

**結論: 本文はどの画面でも幅いっぱい。画面ごとに幅を変えない。**

#### 2度失敗している。同じ道を戻らないこと

1. **1度目**: 各ページが独自に `max-w-3xl` `max-w-5xl` を書いていた。幅が画面ごとに違うと、
   利用者には「壊れている」か「作りかけ」に見える。
2. **2度目**: これを `screens.ts` の `width`（`wide` / `narrow`）に集約した。**が、`narrow` に
   した5画面（`/report` `/logic` `/profile` `/ai-settings` `/grid/report`）が今度は
   「右半分が丸ごと空く」状態になり、依頼者から不具合として指摘された。**

2度目の誤りは「正しい原則を、間違った単位に当てた」こと。「1行が長いと読みにくい」は
事実だが、それが効くのは**続けて読む文章**だけ。カード・フォーム・見出し・表は横に伸びても
読む負担が増えない。それをページごと止めると、得るものが無く、右の大きな空白という損だけが残る。

#### 決まりごと

- **ページ全体に幅の上限を掛けない。** `AppShell` の `<main>` は `min-w-0 flex-1` だけを持つ。
- 読み幅を制限してよいのは**続けて読む文章1ブロック**だけ。**箱ではなく行**に掛ける。
  - `.prose-note :where(p, li)` → `max-width: 42em`（`Prose` の中の段落・箇条書き）
  - `.readable` → `max-width: 42em`（`Prose` の外にある長文に手で付ける。AI生成文など）
- 単位は `ch` ではなく **`em`**。`ch` は欧文の「0」の字幅が基準で、全角の日本語では想定より広くなる。全角1字 = 1em なので、`em` はそのまま「1行あたりの字数」になる。42em ≒ 42字。
- **箱に掛けてはいけない理由**: `.prose-note` は `ScreenHeader` の役割カードのように「文章ではない面」にも付いている。箱ごと狭めるとその面まで縮む。§11-7 の「表に `max-width` を掛けてはいけない」と同じ種類の失敗。
- `.readable` を付ける対象は「途切れずに続く文章」だけ。見出し・数字・ラベル・ボタンには付けない。

#### 新しい画面を足すときに自動で守られる仕組み

`tests/lib/contentWidth.test.ts` が3方向から塞いでいる。**画面名を列挙していない**ので、
まだ存在しない画面にも効く。

| 検証 | 落ちる条件 |
|---|---|
| `app/(app)` 配下を丸ごと走査 | ページに `max-w-2xl` 〜 `max-w-7xl` を書いた |
| `AppShell` の `<main>` 行 | `max-w-*` または `mx-auto` を足した |
| `screens.ts` | `width:` / `ScreenWidth` を復活させた |

例外として許すのは**部品の中の1要素**に効く上限だけ（入力欄1つの幅、札の文字数上限、
ダイアログの幅）。これらは `max-w-xs` `max-w-sm` `max-w-md` の範囲に収まるので検出されない。

**「この画面だけ狭くしたい」と思ったら**、幅ではなく中身の並べ方で解く（カードを2列にする、
関係の薄い塊を折りたたむ）。幅を狭めても情報量は減らず、空白が増えるだけ。

### 11-12. ボタンの見た目とラベル（画面ごとに書き起こさない）

依頼者の指摘（2026-08-09）:

> 視覚的にわかるように文字とボタンを配置していますが、これだと分かりにくかったり、逆に鬱陶しいところがあるので、この辺はアイコンで表示するなどの工夫をしてください。
> 毎回それを一つ一つ改善するってなると手間なので**共通化**しておいてください。**全ての内容でこれを言えること**です。

**見た目は `app/globals.css` の `.btn` 系だけが持つ。** 画面側で `rounded-md border px-3 py-1 …` を
書き起こさない。書き起こすと、同じ「削除」でも画面ごとに高さも丸みも違ってしまう。

| クラス | 使う場面 |
|---|---|
| `.btn-primary` | その画面で最後に押すもの（取り込む・確定する・次へ） |
| `.btn-secondary` | 途中で押すもの（ここまでを保存・書き出す） |
| `.btn-quiet` | 戻る・閉じる・開くなど、押しても取り返しがつくもの |
| `.btn-danger` | 消す・止める。取り返しのつきにくいもの（削除・凍結・ログアウト） |
| `.btn-sm` | 表の行や一覧の中に置く小さい操作。高さだけを落とす |

**下線（`underline`）はリンクの意味に固定する。** 押すと別の画面へ行くものだけが下線を持つ。
その場で処理が走るだけのボタンに下線を使うと、戻れると思って押した人が迷う。

**ラベルは動詞で終える。** 「削除」「取消」「メニュー」のような名詞1語は、押したら何が起きるかを
言っていない。「このユーザーを削除する」「この招待を取り消す」「メニューを隠す」と書く。
行き先を持つものは行き先の名前を `app/_lib/screens.ts` から取り、画面ごとに呼び名を作らない
（「データ取込」を、ある画面だけ「月次データ取込」と呼ばない）。

以上3点は `tests/lib/buttonStyle.test.ts` が `app/(app)` 全体を走査して固定する。

### §11-13. 表・定義リスト・札・貼り付ける帯（2026-08-11 追加）

依頼者の指摘（2026-08-11）で「何でも表になっている」「見えていてほしい情報が
スクロールで消える」「ラベルが実態と合っていない」が挙がった。判断基準の本体は
**`docs/product/T7-ui-conventions.md`** にあり、ここでは部品の対応だけを示す。

| やりたいこと | 使う部品 | 要点 |
|---|---|---|
| 値を見比べる | `DataTable` | `maxHeight` を渡したときだけ列見出しが固定される（理由は T7 §2-1） |
| 1件を読んで判断する | `DefinitionList` | `<dt>`/`<dd>` を `<dl>` の外に書かない |
| 絞り込み条件・件数を上に貼る | `StickyFilterBar` | 工程タブがある画面は `below="stepHeader"` |
| 状態・重大さの札 | `Badge` | 色は4つだけ。「目立たせたい」ではなく「意味がこれだから」で選ぶ |
| 話題の変わり目 | `SectionHeading` | 区切り線だけを引かない。必ず見出しと組で使う |
| 素のフォームの欄 | `formStyles.ts` の `FIELD_CLASS` 他 | 画面にクラス列を書き写さない |
| ログイン等シェル外の枠 | `AuthShell` | アプリ内と同じフッターを出す |

**訳の表は1箇所ずつしか持たない**（同じ表が複数あると片方だけ直る）:
`app/_lib/fieldLabels.ts`（収支表の項目）/ `severity.ts`（重大さ）/
`factorLabels.ts`（赤字の要因）/ `kindLabels.ts`（AIの呼び出し・帳票の種類）。
**画面に英語のキーをそのまま出さない。**
