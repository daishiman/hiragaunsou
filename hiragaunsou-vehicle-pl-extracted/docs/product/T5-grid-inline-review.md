# T5 月次収支表の「その場で直す / OKにする / まとめて反映」設計メモ

対象画面: 月次収支表 (業務フロー STEP8) `/grid`
対象の困りごと: 指摘の付いたセルを直すのに車両詳細へ移動する必要があり、1件直すたびに月全体の再計算が走る。

---

## 0. 依頼者の素案と、採用した仕様

| # | 素案 | 採用 | 理由 |
|---|---|---|---|
| 1 | セルをダブルクリックで編集 | 採用(＋Enter/F2でも開始) | ダブルクリックだけだとキーボード操作の人が使えない |
| 2 | 指摘に「OK」を付けられる | 採用(名前は「確認済みにする」) | 「OK」は何がOKか曖昧。既存画面の語(確認/判定)に合わせる |
| 3 | 全部確認し終わってからまとめて再計算 | **一部変更**: 直した値は即保存し、再計算だけを溜める | 「まとめて」を編集の保存まで含めると、ブラウザを閉じたときに直しが消える |

---

## 1. 前提として確認した既存の作り

- 収支表 `vehicle_pl` は**毎回まるごと作り直される**スナップショット。作り直しの唯一の入口が
  `RecalculateMonthlyPlUseCase`(材料集めを内部に閉じ込め、引数は年月だけ)。
- 人の直しは `vehicle_pl_override`(年月×車番で一意、`values_json` + 理由必須)に置かれ、
  再計算のたびに読み直されて計算の入口の値に重ねられる。**元データ(取込CSV)は書き換えない。**
- 上書きできるのは「計算の入口の値」10項目だけ (`OVERRIDABLE_FIELDS`)。
  損益・経費計・各小計は上書き不可で、必ず再計算で作られる。
- 指摘 (`VehiclePlIssue`) は**DBに持たず、表示のたびに導出**される。出どころは5種類
  (欠落チェック / 異常値フラグ / Excel突合差 / 上書き済みの印 / トレーラ未登録)。
- 「確定」は `vehicle_pl.confirmed`。再計算すると自動的に外れる。

## 2. 論点ごとの比較検討と結論

### 2.1 編集の粒度とコミット単位

| 案 | 内容 | 判定 |
|---|---|---|
| A | セルを直すたびに保存＋再計算 (現状の車両詳細画面) | ✗ 依頼者の不満そのもの |
| B | 全部ブラウザ内に溜めて最後に一括送信 | ✗ 閉じたら消える。106台×51列の未保存状態は事故のもと |
| C | ブラウザ内に溜めつつ、下書きテーブルにも保存 | ✗ 下書きテーブルと上書きテーブルの二重管理になる |
| **D (採用)** | **セル確定で上書きレイヤに即保存。再計算だけを溜め、「まとめて反映」で1回だけ走らせる** | ○ |

D を採る理由:
- 「消えたら困る」のは**直した値と理由**であって、再計算結果ではない。再計算結果はいつでも作り直せる。
  だから永続化すべきは前者だけで、後者を溜めるのが正しい分け方になる。
- 下書き専用テーブルを作らずに済む。`vehicle_pl_override` がそのまま下書き置き場を兼ねる。
- 既存の保存経路(車両詳細の上書き編集)と**同じテーブル・同じ検査・同じ監査ログ**を通る。

未反映を判定する仕掛け: `vehicle_pl_override.applied_at` (nullable) を追加。
- 保存時に `applied_at = NULL` に落とす。
- 「まとめて反映」= 再計算 → **再計算を始めた時刻以前に保存された行だけ** `applied_at` を埋める。
  (再計算中に入った直しを誤って「反映済み」にしないため。)
- 未反映件数 = `applied_at IS NULL` の行数。

**ブラウザを閉じた場合**: 直した値は保存済みなので消えない。次に開くと「未反映の直しが N件」と出る。

### 2.2 再計算の範囲 — 差分再計算はやらない

- 収支表は**全車両を一度に組み立てる**構造 (`FinalizeMonthlyPlUseCase`)。キリン協力金の配賦は
  複数車両に按分され、トレーラはトラクタ行に吸収される。つまり1台の直しが他の行に波及しうる。
  依存グラフを作って部分無効化するのは、この波及を正しく表現するために全体と同じ知識が要る。
- 一方、**回数を1回に減らせば所要時間の問題は消える**。30件の指摘を直すと現状は最大30回走るが、
  この設計では1回になる。差分再計算という難しい仕組みを入れずに、30分の1にできる。
- 結論: **差分再計算は作らない。呼ぶ回数を減らすことで解く。**(残課題にも積まない。必要がない。)
- なお「何秒かかるか」は本番データ量に依存するため、反映ボタンには進行中表示を出し、
  完了後に「◯台分を作り直しました」を返す。実測は preview 確認時に依頼者と一緒に見る。

### 2.3 「確認済み(OK)」の意味論

- **保持する**。画面を開くたびに同じ指摘を見直すのでは、確認作業が終わらない。
- **粒度: 年月 × 車番 × 列 × 指摘の種類**。新テーブル `pl_issue_ack`。
  指摘はDBに無く導出されるので、この4つ組が指摘を指す唯一のキーになる。
- **翌月の再表示ポリシー: 必ず再表示する**(キーに年月が入るため)。
  「先月OKだった」は「今月もOK」の根拠にならない (金額が変われば判断も変わる)。
- **監査**: テーブルに「誰が・いつ・補足メモ」を持ち、加えて既存の監査ログにも1行残す。
- **既存の `review_flag` を使わない理由**: `review_flag` は異常検知の結果だけを保存する箱で、
  Excel突合差や欠落チェックのようにその場で導出される指摘は入っていない。
  導出される指摘をわざわざ全部DBに書き出すと、ルールを直すたびに残骸が残る。
- **値を直したら確認済みはどうなるか**: 指摘そのものが消えれば確認済みも一緒に意味を失う(表示されない)。
  指摘が残る場合は確認済みのまま残す。「値が動いたら自動で確認済みを外す」は、
  丸め1円の修正でも外れてしまい作業が戻るため入れない。

### 2.4 編集値の扱い — 元データは書き換えない

既存の `vehicle_pl_override` をそのまま使う(別レイヤ方式)。再取込しても直しは消えない。
グリッドから直せるのは**上書き可能10項目のうち、表に列がある8項目**
(運行回数 / 伝票件数 / 稼働時間 / 稼働Km / 運賃 / 附帯料金 / 給与 / 福利厚生費)。
乗務員数・賞与(月額)は収支表の列ではないため、従来どおり車両詳細画面で直す。
それ以外の列(燃料費・修理費など)は**専用の入力経路がある**ので編集不可とし、
セルを開こうとしたら「どこで直すか」を案内する(既存の指摘パネルの導線と同じ行き先)。

理由(必須)の扱い: セルの編集欄に理由入力を同居させ、その車両に既に理由があれば初期値として引き継ぐ。
理由を毎回ゼロから書かせず、かつ空のまま保存もさせない。

### 2.5 確定との関係

**確定済みの月は編集も確認済み操作も受け付けない。** 理由は、再計算すると確定が自動的に外れる
既存仕様と衝突するため(直せてしまうと、確定したはずの月が黙って未確定に戻る)。
画面には「確定を取り消してから直してください」と出し、取り消しボタンは既存の確定バーにある。

### 2.6 入力バリデーション

- 対象8項目はすべて数値。**負値は不可**(既存の上書き保存の検査をそのまま使う)。
- 運行回数・伝票件数・乗務員数は整数、稼働Km・稼働時間は小数1桁まで、金額は円単位の整数。
- 不正な入力は保存前にその場で赤字メッセージを出す。サーバ側でも同じ検査が働く
  (画面を経由しない呼び出しでも通るように、判定はユースケースに置いてある既存方針を維持)。

### 2.7 同時編集・競合

**楽観ロック**。編集を開いた時点でその車両の上書きの最終更新時刻を持ち、保存時に送る。
サーバ側で食い違ったら 409 を返し、画面には
「他の人が先にこの車両を直しました。画面を開き直してください」と出す。
車両単位のロック粒度にするのは、上書きが年月×車番の1レコードだからで、
別の列を直していても同じレコードを書き換えるため。

### 2.8 UX / アクセシビリティ

- 編集開始: **ダブルクリック / Enter / F2**。取消: **Esc**。確定: **Enter**。
- セル間移動: 矢印キー・Tab (操作できるセルのみを辿る)。
  表そのものは `<table>` のまま (`role="grid"` は付けない)。付けると読み上げの見出し・行列の対応が
  ネイティブの表として扱われなくなり、51列の表では読み上げが劣化する。代わりに操作できるセルだけを
  タブ移動の対象にし、そのセルに「車番・項目名・値・編集できること」を読み上げ用の名前として持たせる。
- 進捗: 「確認が必要な 30件のうち 12件 確認済み / 残り 18件」を常時表示。0件になったら
  「確認は終わりました。まとめて反映してください」に変わる。
- 未反映のセルは**破線の枠と「反映待ち」**で示す。損益や経費計は反映するまで古い値のままなので、
  「反映するまで下の合計は古いままです」と明記する(黙って古い数字を見せない)。
- 再レンダリング: 保存後に画面全体を取り直さない(再計算していないので他のセルは変わらない)。
  直したセルと件数表示だけを更新する。106行×51列の作り直しが起きない。
- 取り消し: 直した直後は「元に戻す」で1つ前の値に戻せる。車両単位の全取消は従来どおり車両詳細から。

### 2.9 段階的リリース (今回やること / やらないこと)

今回: 上記すべて。ただし以下は**入れない**。
- セル単位の編集履歴画面(監査ログには残るので追える)
- 複数セルのコピー&貼り付け、範囲選択
- 確認済みの一括操作(「この車両の指摘を全部OK」)
- 差分再計算 (2.2 のとおり不要)

## 3. 実装順序 (依存順)

1. **DB**: `0017_add_pl_issue_ack_and_override_applied_at.sql`
   - `vehicle_pl_override.applied_at` 追加 (既存行は反映済みとして `updated_at` を入れる)
   - `pl_issue_ack` テーブル追加
2. **Domain**: 指摘のキー生成と確認済みの重ね合わせ (`plIssueAck.ts`)
3. **Repository**: `PlIssueAckRepository` + 上書きリポジトリに未反映件数・反映済み印
4. **UseCase**: 上書き保存の「反映を後回しにする」対応 / まとめて反映 / 確認済みの登録・取消
5. **API**: `/api/vehicle-pl/override` (defer・楽観ロック) / `/api/vehicle-pl/apply` / `/api/vehicle-pl/issue-ack`
6. **UI**: `/grid` のインライン編集・確認済み・進捗・まとめて反映
