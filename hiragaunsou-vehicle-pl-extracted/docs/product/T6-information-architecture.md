# T6 情報設計 — 画面の役割分担 (2026-08-09)

依頼者から出た指摘:

> 「データ整形」「手入力」「チェック」がそれぞれ似たようなことをしていて、どれを見て確認すべきか曖昧。
> マスタ管理も複数ある。「月次収支表」と「年間集計・対前年」も似た項目に見える。
> 初心者が直感的に見て分かるようにしてほしい。

**方針: 画面は1つも消さない。** どれも実際の業務で必要な工程で、消せば別の場所に同じ操作が必要になる。
曖昧さの原因は機能の重複ではなく **名前と説明が画面ごとにばらばらだったこと** なので、
情報設計(名前・並び・説明の言い回し・画面同士の関係)だけで解く。

---

## 1. 画面の棚卸し（23画面・重複なし）

骨格は「一覧なら表」「今風ならカード」で決めない。誰がどの頻度で、一度に何件を読む・比べる・入力する・判定するかから導く。
特に、大量の同一項目を突き合わせる画面で表を選ぶことは、簡素化に反しない。

| グループ | 画面（パス） | 主目的 | 想定利用（頻度 × 習熟度） | 骨格と理由 |
|---|---|---|---|---|
| 儲かっているかを見る | ダッシュボード（期間指定） `/dashboard` | 任意期間の損益と異常を俯瞰する | 週次〜月次 × 中級者 | 主数字 → 要対応 → 内訳。最初の意思決定順を写す |
| | 赤字の理由 `/deficit` | 赤字車両を原因別に分けて打ち手を決める | 月次 × 中級者 | 原因別グループ + 車両リスト。状態分類と対象の比較を同時に保つ |
| | AI要因分析 `/report` | 損益の動きを説明文と根拠数値にする | 必要時 × 中級者 | 実行CTA → 要約 → 根拠。生成文より先に対象と費用を明示する |
| 毎月の締め | ホーム `/` | 今月の次の作業を1つ決める | 日次〜月次 × 初心者〜熟練者 | 進捗 + 次の1操作。選択肢を並べず迷いを減らす |
| | 1 データ取込 `/import` | 複数の原本ファイルを正しい月へ取り込む | 月次 × 初心者〜熟練者 | 段階パネル + 取込キュー。処理状態とファイル単位の結果を分ける |
| | 2 データ整形 `/cleansing` | 伝票を残す・付け替える・外すと判定する | 月次・複数件 × 初心者〜熟練者 | 1件判定パネル + 進捗。周囲の伝票をノイズにせず根拠と操作に集中する |
| | 3 手入力 `/manual-entry` | 請求書と突き合わせながら車両別の金額を入れる | 月次・大量 × 初心者〜熟練者 | キーボード操作できる表。同じ項目の縦比較と連続入力が主目的 |
| | 4 チェック（1件ずつ） `/anomaly` | いつもと違う値を入力ミスか実績か判定する | 月次・複数件 × 初心者〜熟練者 | 1件ウィザード + 比較材料。一度の判断を1つに限る |
| | 要確認の一覧（まとめて） `/todo` | 未判定を漏れなく探し、全体量を把握する | 月次・多件数 × 熟練者寄り | 絞り込み付き高密度リスト。判定より検索・件数把握を優先する |
| できあがった収支表（締め 5 / 5 を兼ねる） | 月次収支表（1か月・車両ごと） `/grid` | 51項目を車両間で突合・修正し、月を確定する | 月次・106台想定 × 初心者〜熟練者 | 表 + 1件集中モード。全体の突合と初心者の判定を無理に同じ器で解かない |
| | 確認の記録（印刷） `/grid/report` | 誰が何を直し・判定したかを紙とURLで共有する | 月次・閲覧中心 × 初心者〜中級者 | 印刷文書 + 正確値の表。画面操作より追跡性と紙面の参照順を優先する |
| | 年間集計（1年・月ごと） `/annual` | 1年の推移と前年差を月単位で比べる | 月次 × 中級者 | 主数字 + 月別比較表。時系列と正確な金額の両方を保つ |
| | 車両1台の明細 `/vehicle/[vehicleNo]` | 1台の内訳と12か月の動きを追う | 必要時 × 中級者 | 主数字 + 内訳 + 月別表。1件の階層と時間関係を上から読む |
| 計算の基準 | 率マスタ設定 `/rate-settings` | 全車両に効く率と単価を編集する | 必要時・少項目 × 熟練管理者 | 定義行 + 編集フォーム。影響範囲を値と常に対応させる |
| | 車両マスタ管理 `/admin/vehicle-master` | 車両別の属性と固定費をまとめて編集する | 必要時・大量 × 熟練管理者 | 編集表。同じ項目の縦比較・差分保存・連続入力を優先する |
| | 運転者マスタ管理 `/admin/driver-master` | 社員Noと車番の対応をまとめて編集する | 必要時・大量 × 熟練管理者 | 編集表。突合とキーボード入力を優先する |
| 仕組みの説明 | データ設計・自動化方針 `/logic` | 収支表の数字の出どころと計算規則を調べる | 必要時 × 初心者〜熟練者 | 項目別の参照表 + 詳細開示。検索性と根拠への到達を優先する |
| アカウント・管理 | マイページ `/profile` | 自分のアカウント情報を確認・変更する | 必要時 × 初心者 | 少数項目のフォーム。1件の安全な変更に集中する |
| | 利用状況 `/usage` | AI利用量と概算費用を確認する | 月次 × 中級者 | 主数字 + 利用内訳表。概算と根拠を分けて読める |
| | AI設定 `/ai-settings` | AIに使うAPIキーを登録・失効する | 必要時 × 熟練管理者 | 登録フォーム + 状態リスト。秘密値そのものは再表示しない |
| | 利用者の管理 `/admin/users` | 権限・凍結・招待を利用者ごとに管理する | 必要時・複数件 × 熟練管理者 | 管理表 + 行アクション。一覧性を保ち、破壊的操作だけを分離する |
| | 取込データ管理 `/admin/import-batches` | 取込履歴を追跡し、誤取込を特定する | 必要時・多件数 × 熟練管理者 | 監査台帳表。正確な時刻・原本・実行者を同一行で追う |
| 直した内容の反映 | 直した内容の反映 `/master-changes` | マスタ変更を締め済みの月に反映するか判定する | 必要時・複数月 × 熟練管理者 | 影響一覧表 + 判定パネル。対象年月の比較と高リスク操作の確認を分ける |

「月次収支表」はサイドバー上では「できあがった収支表」に1回だけ属し、同時に毎月の締め 5 / 5 を兼ねる。
以前の表のように2グループに重複計上しない。`/grid/report` はサイドバーには出さないが、独立した1画面として数える。

## 2. 重複していた組み合わせと、どう整えたか

いずれも **機能はそのまま**、名前・説明・並びだけを変えた。

| 紛らわしかった組み合わせ | 何が違うのか | 打ち手 |
|---|---|---|
| データ整形 / 手入力 / チェック | 整形=売上伝票の可否判定、手入力=請求書の金額入力、チェック=できた数字の妥当性判定。**扱うデータも保存先も別** (§4) | 3画面に「毎月の締め n / 5」を表示。役割が紛らわしい画面だけ「ここでは見ないこと」で互いを名指しする |
| チェック(1件ずつ) / 要確認の一覧 | **中身は同じ。見せ方だけが違う** | 一覧をサイドバーの「補助ツール」から「毎月の締め」のチェックの真下へ移動。名前を「チェック(1件ずつ)」「要確認の一覧(まとめて)」に変え、互いを「同じ内容の別の見方」として指し合う |
| 月次収支表 / 年間集計・対前年 | 1か月×車両ごと / 1年×月ごと | 見出しと一覧名の両方に「1か月・車両ごと」「1年・月ごと」を入れ、名前だけで見分けられるようにした |
| ダッシュボード / 年間集計 | 期間を自分で決める / 1年で固定 | 「ダッシュボード(期間指定)」に改名 |
| 3つのマスタ画面 / 直した内容の反映 | 前者は登録、後者は登録した結果の影響確認 | 「計算の基準(先に登録しておく)」と「直した内容の反映(最後に確認)」の2グループに分け、後者をサイドバー最下部へ |
| マスタ管理 / 取込データ管理 | 計算の基準 / 取り込んだファイルの後始末 | 取込データ管理は「アカウント・管理」グループへ (業務ではなく運用の画面) |

## 3. どの画面でも答えられるようにする意味契約

「この画面ですること / ここでは見ないこと / 終わったら次に」は、情報設計で答えるべき**意味の契約**である。
全画面に3行の説明カードを常時表示する見た目の契約ではない。操作と配置で伝わることを説明文で重複させない。

| 意味 | `ScreenDef` | 必須条件 | 画面上での出し方 |
|---|---|---|---|
| この画面ですること | `does` | **全画面で必須** | リード文または役割ノートに1回だけ出す。主要CTAと同じ動詞を使う |
| ここでは見ないこと | `notHere` | 紛らわしい兄弟画面、または誤操作に直結する境界があるとき | 役割ノートに行き先とともに出す。境界が明白な単独画面に空の行は出さない |
| 終わったら次に | `next` | 工程に属する画面、または明確な次の行き先があるとき | 主要CTAまたは工程ナビとして出す。説明行とCTAの二重表示にしない |

毎月の締めの5画面では **「毎月の締め n / 5」** と前後の工程を同じ位置に出す。
一方、印刷・共有用の `/grid/report` は作業工程ではない。文書見出し、対象月、出力時点、戻る/印刷の操作が契約を満たすため、通常の役割ノートを出さない。

文言は画面のJSXではなく `app/_lib/screens.ts` の対応する定義が持つ。サイドバー・ページ見出し・
前後リンクはすべてそこから作られるので、**サイドバーの並びと画面内の案内がずれることが構造上起きない**。
実装規約は `docs/design-system-components.md` §11。

## 4. 「データ整形」と「手入力」の違い (コード上の事実)

| | データ整形 | 手入力 |
|---|---|---|
| 元になる書類 | 売上モニタリストCSV (車楽クラウド出力) | 紙の請求書・レシート |
| 読むテーブル | `raw_ingestion` (`source_type = "sales_monitor"`) | `manual_vehicle_input` (前回入力の読み戻し) |
| 決めること | 伝票1行ごとの可否（収支計算から外す / 直す / このままでよい） | 金額・数量（燃料・修繕・タイヤ・高速など） |
| 書くテーブル | `cleansing_decision` | `manual_vehicle_input` |
| 元データ | 書き換えない (判断だけを別に持つ) | 入力値そのものを保存 |

両者は独立していて、収支表を組み立てる `finalizeMonthlyPl` が両方を読み合わせて `vehicle_pl` を作る。

**「直す」で車番とメモしか直せないのは、未実装ではなく設計上そうしている。**
車番を直すと、その伝票の金額はまるごと新しい車番の集計に移る (`applyCleansingDecisions` が
車番だけ差し替え → `aggregateSalesByVehicle` が車番ごとに合算)。つまり **車番さえ正しければ金額は自動で正しい車に乗る**。
金額そのものの誤りは元のCSV側の問題で、この画面の対象外。

## 5. 意図的に採らなかった案

- **画面を統合して数を減らす** — 工程が消えるわけではないので、1画面に複数の目的が同居して
  かえって分かりにくくなる。名前と説明で解けるうちは画面を減らさない。
- **チェックと要確認の一覧をタブに統合する** — URLが変わり、既存のリンク・テストが壊れる。
  隣に並べて「同じ内容の別の見方」と書けば十分だった。
- **業務フローのSTEP番号バッジを全画面に戻す** — 以前「初心者に分かりにくい」として廃止した経緯がある
  (`tests/lib/navigation.test.ts`)。番号は毎月の締めのヘッダ内 (n / 5) にだけ出す。

## 6. サイドバーの認知負荷を下げる (2026-08-09 追記)

依頼者の追加指摘:

> サイドバーに情報が膨大にありすぎて認知負荷がかなり高い。畳んだときの件数は要らない。
> 「絶対にこの情報がないと分からない」という情報だけを表示する形に整えてほしい。

§1〜§5 で決めた **画面の役割分担・名前・グループはそのまま**、
「どこに出すか」と「何を常時見せるか」だけを見直した。**画面は1つも消していない。**

| 変更 | 内容 |
|---|---|
| 置き場所の分離 | グループに `placement` を持たせ、業務の画面 (5グループ) をサイドバー、運用・設定・仕様書 (2グループ) をユーザー名から開くアカウントメニューへ |
| 折りたたみの廃止 | グループ見出しは押せないラベルに。中の項目は常に見え、どの画面にも1クリックで着く |
| 件数表示の廃止 | 畳んだときの項目数と、データ取込の登録台数バッジを削除。残したのはチェックの未判定件数だけ |
| 案内バッジの廃止 | ホームの「まずはここ」を削除 (位置と面の色ですでに伝わっている) |
| サイドバー自体の表示切替 | ヘッダに `メニューを隠す` / `メニューを表示`。状態は次に開いたときも保持する |
| フッタの重複リンク削除 | データ設計・利用状況・月次データ取込の3本は、サイドバーとアカウントメニューに同じものがある |

置き場所の判断基準は `docs/design-system-components.md` §11-9。頻度の根拠は `docs/product/data-flow-map.md` §1 の
STEP対応表 (毎月の締めで往復するのは `/import` `/cleansing` `/manual-entry` `/anomaly` `/grid` の5画面)。

**採らなかった案**

- **常時展開のうえグループの並びも変える** — 「分析が主目的」という既存の決定 (`tests/lib/navigation.test.ts`)
  を覆すことになる。締めの頻度が高いのは事務、分析の頻度が高いのは経営者で、頻度は役割で逆転する。
  並びで解かず、権限による出し分け (`visibleScreens`) に任せる。
- **現在地のグループだけ自動展開 (アコーディオン)** — 開く場所が動くと毎回どこを見ればよいか探し直しになる。
  常時1クリックの原則も崩れる。
- **畳んでアイコン列だけ残す (macOS/Xcode 風)** — 「率マスタ設定」「直した内容の反映」のような業務語は
  アイコンで表せない。ツールチップ必須になり、結局ホバーしないと分からない状態を作る。
- **毎月の締めだけ常時見せて他を畳む** — 経営者は締めを操作しない。役割によって「毎月の締め」が
  一度も使われないので、非対称な扱いが裏目に出る。
