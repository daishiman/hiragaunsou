# UI/UX 設計判断台帳

作成日: 2026-08-11
対象: 車両別収支管理システムの全画面

## 1. この台帳の責務

本書は、通常の画面契約を重複して持たない。責務は次のように分ける。

- `T1-requirements.md`: 利用者、利用場面、業務成果、UI品質の計測値
- `T2-experience-spec.md`: 全画面に必須の `ScreenExperienceContract`
- `T5-grid-inline-review.md`: `/grid` 固有の表・確認モードの判断
- `T6-information-architecture.md`: 画面の責務、名称、配置、遷移
- `docs/design-system.md`: 視覚表現と共通部品の実装規律
- **本書**: 前例のない例外判断、却下案、検証結果、汎用化の可否

同じ判断が3画面以上で有効だった場合だけ、プロジェクト共通規律またはエージェントキットへの昇格を検討する。記事の事例をそのまま模倣することはしない。

## 2. 入力資料と画像分析

入力資料は、Qiita記事「[なぜエンジニアが作る画面はダサいのか…?](https://qiita.com/mskmiki/items/544149987475719e417b)」の本文と掲載画像である。

画像から確認した差は次のとおり。

- A案は表、全項目ラベル、格子罫線、説明文、同格のボタン、分類色を積み上げ、視線の起点が分散している。
- B案は利用場面を先に置き、人物識別、直近の予約・行動、履歴の順に群化し、余白、位置、文字サイズ、相対表現、意味のあるアイコンで優先順位を示している。
- 差を生んだのはカードや色そのものではなく、`利用場面 → 削減と補完 → 群化 → 優先順位 → 表示加工 → 器 → 機能 → 意味の装飾` の順序である。
- 記事自身もB案を普遍的な最適解とはしていない。本システムの106台×51列の突合・入力・監査へカードを一律適用すると、一覧性と処理速度が落ちる。

## 3. 採用した設計判断

### UI-001: 表かカードかではなく、仕事から器を導く

- 場面: 初心者が要確認を1件ずつ判断する一方、熟練者は多数行を比較・修正・一括反映する。
- 採用: 初心者は1件ウィザード、熟練者は高密度表を使う。読む、探す、比較、入力、1件判断、一括処理、監査・出力の主目的ごとに器を導出する。
- 決め手: 利用頻度×習熟度と、作業の空間構造が異なる。
- 却下: 全画面カード化、全画面表形式、利用者に既定を決めさせるだけの無目的な表示切替。
- 検証: 初心者の完了時間を短縮し、熟練者の30件処理時間を悪化させない。

### UI-002: 役割情報は保持し、説明文の常時表示とは分ける

- 場面: 似た工程の区別には `does / notHere / next` が必要だが、全画面に同じ3行を常時出すと反復ノイズになる。
- 採用: `does` は全画面の意味契約として必須。`notHere` は紛らわしい兄弟画面がある場合、`next` は工程上の次行動がある場合だけ表示する。帳票・印刷は明示例外とする。
- 却下: 3行を全画面で常時表示すること、意味契約自体を削除すること。
- 検証: 説明カードを読まなくても主操作を開始でき、迷った場合は区別と次行動へ到達できる。

### UI-003: 表示用加工と監査値を別レーンにする

- 場面: 管理閲覧では業務語・要約・相対表現が速いが、突合・入力・印刷・監査では正確値が必要。
- 採用: 閲覧は共通formatterで人向けに加工し、正確値への復路を必ず残す。突合・入力・出力・監査はraw値を正とする。
- 却下: DB値の無加工表示を全画面へ強制すること、相対日時や丸め値だけで原値を隠すこと。
- 検証: 表示値から原本・取込バッチ・正確日時・正確金額へ追跡できる。

### UI-004: 視覚要素は「無いと何を誤読するか」で決める

- ラベル: 値だけでは意味が一意にならない表示、入力、表ヘッダー、支援技術では残す。
- 線: 余白と整列だけでは境界を誤読する場合に限る。
- アイコン: 押す前の結果が一意な既知操作に限る。業務操作は動詞ラベルを残す。
- 画像: 対象の識別、原票の証拠、文章より速い説明のいずれかを担う場合だけ使う。飾りなら削る。
- 強調: 色を増やさず、位置、余白、サイズ、太さを先に使う。状態は文字・形も併用する。

### UI-005: プロジェクトで実証してから汎用化する

- 採用: `T1 → T2 → T5/T6 → design-system → screens/components/formatter → tests` の順で反映する。
- 却下: 記事から配布スキルへ直接一般化し、プロジェクト固有の制約を後付けすること。
- 昇格条件: 同じ判断が3画面以上で有効、実データと4幅で再現、既存機能と監査経路を失わないこと。

## 5. 完了ゲート

次を同時に満たしたときだけ、この改善を完了とする。

- 矛盾なし: 表/カード、常時説明/省略、raw/加工の適用条件が明文化されている。
- 漏れなし: 30思考法、記事本文・画像の示唆、ラベル・線・アイコン・画像、全画面契約、検証条件が反映されている。
- 整合性あり: 用語と正本責務がT1/T2/T5/T6/design-system/本書で重複していない。
- 依存関係整合: 参照先が実在し、上流仕様から実装・テスト・配布ミラーへの順序が追跡できる。
