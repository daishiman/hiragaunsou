# UI/UX 設計判断台帳

作成日: 2026-08-11
対象: 車両別収支管理システムの全画面

## 1. この台帳の責務

本書は、通常の画面契約を重複して持たない。責務は次のように分ける。

- `T1-requirements.md`: 利用者、利用場面、業務成果、UI品質の計測値
- `T2-experience-spec.md`: 全画面に必須の `ScreenExperienceContract`
- `T5-grid-inline-review.md`: `/grid` 固有の表・確認モードの判断
- `T6-information-architecture.md`: 画面の責務、名称、配置、遷移
- `docs/design-system.md`: 視覚表現と共通部品の実装規律
- **本書**: 前例のない例外判断、却下案、検証結果、汎用化の可否

同じ判断が3画面以上で有効だった場合だけ、プロジェクト共通規律またはエージェントキットへの昇格を検討する。記事の事例をそのまま模倣することはしない。

## 2. 入力資料と画像分析

入力資料は、Qiita記事「[なぜエンジニアが作る画面はダサいのか…?](https://qiita.com/mskmiki/items/544149987475719e417b)」の本文と掲載画像である。

画像から確認した差は次のとおり。

- A案は表、全項目ラベル、格子罫線、説明文、同格のボタン、分類色を積み上げ、視線の起点が分散している。
- B案は利用場面を先に置き、人物識別、直近の予約・行動、履歴の順に群化し、余白、位置、文字サイズ、相対表現、意味のあるアイコンで優先順位を示している。
- 差を生んだのはカードや色そのものではなく、`利用場面 → 削減と補完 → 群化 → 優先順位 → 表示加工 → 器 → 機能 → 意味の装飾` の順序である。
- 記事自身もB案を普遍的な最適解とはしていない。本システムの106台×51列の突合・入力・監査へカードを一律適用すると、一覧性と処理速度が落ちる。

## 3. 採用した設計判断

### UI-001: 表かカードかではなく、仕事から器を導く

- 場面: 初心者が要確認を1件ずつ判断する一方、熟練者は多数行を比較・修正・一括反映する。
- 採用: 初心者は1件ウィザード、熟練者は高密度表を使う。読む、探す、比較、入力、1件判断、一括処理、監査・出力の主目的ごとに器を導出する。
- 決め手: 利用頻度×習熟度と、作業の空間構造が異なる。
- 却下: 全画面カード化、全画面表形式、利用者に既定を決めさせるだけの無目的な表示切替。
- 検証: 初心者の完了時間を短縮し、熟練者の30件処理時間を悪化させない。

### UI-002: 役割情報は保持し、説明文の常時表示とは分ける

- 場面: 似た工程の区別には `does / notHere / next` が必要だが、全画面に同じ3行を常時出すと反復ノイズになる。
- 採用: `does` は全画面の意味契約として必須。`notHere` は紛らわしい兄弟画面がある場合、`next` は工程上の次行動がある場合だけ表示する。帳票・印刷は明示例外とする。
- 却下: 3行を全画面で常時表示すること、意味契約自体を削除すること。
- 検証: 説明カードを読まなくても主操作を開始でき、迷った場合は区別と次行動へ到達できる。

### UI-003: 表示用加工と監査値を別レーンにする

- 場面: 管理閲覧では業務語・要約・相対表現が速いが、突合・入力・印刷・監査では正確値が必要。
- 採用: 閲覧は共通formatterで人向けに加工し、正確値への復路を必ず残す。突合・入力・出力・監査はraw値を正とする。
- 却下: DB値の無加工表示を全画面へ強制すること、相対日時や丸め値だけで原値を隠すこと。
- 検証: 表示値から原本・取込バッチ・正確日時・正確金額へ追跡できる。

### UI-004: 視覚要素は「無いと何を誤読するか」で決める

- ラベル: 値だけでは意味が一意にならない表示、入力、表ヘッダー、支援技術では残す。
- 線: 余白と整列だけでは境界を誤読する場合に限る。
- アイコン: 押す前の結果が一意な既知操作に限る。業務操作は動詞ラベルを残す。
- 画像: 対象の識別、原票の証拠、文章より速い説明のいずれかを担う場合だけ使う。飾りなら削る。
- 強調: 色を増やさず、位置、余白、サイズ、太さを先に使う。状態は文字・形も併用する。

### UI-005: プロジェクトで実証してから汎用化する

- 採用: `T1 → T2 → T5/T6 → design-system → screens/components/formatter → tests` の順で反映する。
- 却下: 記事から配布スキルへ直接一般化し、プロジェクト固有の制約を後付けすること。
- 昇格条件: 同じ判断が3画面以上で有効、実データと4幅で再現、既存機能と監査経路を失わないこと。

### UI-006: 不満は「困っている画面の上」で受け取る (2026-08-15 追記)

- 場面: 業務中の利用者が「ここが使いにくい」と感じた瞬間。困った対象を見ながらでないと、何が変かを言葉にできない。
- 採用: 全画面の右下に固定ボタンを置き、その場でダイアログを開く。開くと同時に画面の写しを自動で撮り、写しの上へ直接描き込める。
- 決め手: 主目的は「入力」だが、入力できる状態を作るのが最大の障壁だという点。要望フォームへ移動した時点で、指摘の対象が視界から消える。
- 却下: (a) 独立した要望画面 — 移動で対象が消え、URLも手で書かせることになる。
  (b) 画面録画API (`getDisplayMedia`) — ブラウザの共有許可ダイアログで流れが切れ、共有先を利用者に選ばせてしまう。
  (c) 送信後のメール/チャット連携 — 届け先が増えるだけで、どの画面の話かは相変わらず本人の記述に頼る。
- 採用した撮り方: DOM を描き直す方式 (`modern-screenshot` の `domToCanvas`)。このアプリの図表は div と SVG のため忠実に写る。
  canvas / iframe が増えたときは写りが崩れるので、その要素数を数えて画面上で警告する。
- 検証: 本文が空なら押す前に理由を出す。写しが撮れなくても本文だけで送れる。閉じても未送信の内容が残る。

### UI-007: 実URLと集計単位を両方持つ (2026-08-15 追記)

- 場面: 同じ「車両1台の明細」への同じ指摘が、車番の数だけ別件に見える。
- 採用: `path` (クエリを落とした実URL) と `routePattern` (`/vehicle/[vehicleNo]`) の2つを保存し、
  件数は `routePattern` で数え、再現の手がかりとして `path` を詳細に出す。
- 却下: (a) 実URLだけを持つ — どの画面が一番困られているかが読めない。
  (b) 画面パターンだけを持つ — どの車両を見ていたかが失われ、再現できない指摘が増える。
  (c) 送信側が画面名を名乗る — 画面を足したときに名乗りだけ古くなる。台帳 (`screens.catalog.ts`) から引く。
- 副次: クエリを落とすのは集計のためだけではない。対象月・検索語が要望に貼り付くと、送った本人が意図しない情報が管理者の一覧に並ぶ。

### UI-008: 「対応済み」「見送り」で終わりにしない (2026-08-15 追記)

- 場面: 管理者が届いた声を判定する。取り違えて閉じることが必ず起きる。
- 採用: どの状態からでも他の状態へ戻せる。禁じるのは「状態もメモも変わらない保存」だけ。見送りだけは理由を必須にする。
- 決め手: 戻せない終端状態を作ると、閉じ間違いが「要望そのものの消失」と同じになる。理由の無い見送りは、送った人から見れば黙殺と同じ。
- 却下: 完了/却下を終端にして再オープンを別操作にすること (操作が増え、実際には誰も戻さなくなる)。

## 5. 完了ゲート

次を同時に満たしたときだけ、この改善を完了とする。

- 矛盾なし: 表/カード、常時説明/省略、raw/加工の適用条件が明文化されている。
- 漏れなし: 30思考法、記事本文・画像の示唆、ラベル・線・アイコン・画像、全画面契約、検証条件が反映されている。
- 整合性あり: 用語と正本責務がT1/T2/T5/T6/design-system/本書で重複していない。
- 依存関係整合: 参照先が実在し、上流仕様から実装・テスト・配布ミラーへの順序が追跡できる。

## 7. 送信時の記録と Issue 起票の例外判断 (2026-08-15)

通常の画面判断は T2 S4 に置いた。ここに残すのは、既存の設計語彙に前例が無く、
同じ場面が来たときに同じ答えを出したい4件だけ。

| 場面の1文 | 選んだ形 | 決め手の軸 | 却下した候補と理由 |
| --- | --- | --- | --- |
| 直す側が知りたいことを、送る人に入力させずに集めたい | 送信時に裏で自動収集し、送る人には1欄も足さない | 主目的（入力）と利用特性（低頻度・低習熟）。欄を足すと本文まで書かれなくなる | 「ブラウザ名を選んでください」等の追加入力（そもそも答えられない）／聞き直し（1往復増える間に再現しなくなる） |
| 集めた記録を管理画面のどこに置くか | 既定で畳む `<details>` を1枚のカード内に積む。空でも枠を残し「取得不可」と書く | 情報量と閲覧頻度。毎回読むものではないが、無いことは分かる必要がある | 一覧に出す（件数が増えるほど読まれない）／空なら非表示（集め忘れと区別できない） |
| 番号が起票後にしか分からないのに、二重起票を防ぎたい | 「作業中の印」の列（60秒で自然に切れる）＋ 番号の一意索引の2段 | 一意索引は NULL を別物として扱うため、未起票の行は何行でも共存できる | 確認→起票→保存だけ（同時押しで2本立つ）／番号列に仮の値を入れる（一意索引に阻まれ、全体で1行しか持てない） |
| 外部（GitHub）へ出す内容に、どこまで載せるか | 原文にも値の形のマスクをかけ、画面の写しは既定で出さずアプリ内リンクにする | 会社境界。中で見る分には安全でも、外へ出た時点で取り消せない | 写しをそのまま添付（取り消せない）／原文を無加工で載せる（本人が誤って書いた値がそのまま外に残る） |

### 7-1. 3層の仕分けを追記 (2026-08-15 確定分)

| 場面の1文 | 選んだ形 | 決め手の軸 | 却下した候補と理由 |
| --- | --- | --- | --- |
| どこまで集めれば再現でき、どこからは持つだけ危ないのか | 「必ず集める / 条件付き / 集めない」の3層に仕分け、集めないものをコードのコメントに列挙する | 再現できるかと、漏れたときの被害の大きさ。Cookie・本文・DOM全体は「あれば便利」だが無くても再現できる | 全部集める（漏れたときの被害が業務データそのものになる）／エラーだけ集める（どの操作から来たかが分からず再現できない） |
| うまくいった通信をどこまで残すか | 記録は残さず、所要時間の数だけ数える。3秒を超えたものだけ記録として残す | 情報量。正常の記録が枠を埋めると、肝心の失敗が古い順に捨てられる | 全件記録（枠を埋める・持ち出し口が増える）／一切記録しない（「この画面が遅い」という要望を確かめられない） |
| 同じデータでも、保存してよい量と外へ出してよい量は同じか | 「集める量 / 保存する量 / 外へ出す量」を別々に決める。Issue に載せる量は D1 より少なくする | 取り消せるか。Issue は編集履歴と通知メールが残り、読む人の範囲も管理画面と違う | 保存したものをそのまま Issue へ（氏名・実URL・応答本文が社外の場所に永久に残る）／Issue には何も載せない（管理画面を開き直さないと着手できず、Issue が「通知」になる） |
| 黒塗りを「隠したつもり」で終わらせないために何を保証するか | 元画像のピクセルを塗りつぶした1枚だけを保存・送信し、元画像は持たない。塗った下が取れないことをテストで固定する | 取り消せるか。重ねる方式だと、保存先・送信・後から作る書き出しのどこか1つで元が出る | 印を別レイヤーで持つ（元画像が残る）／表示のときだけ隠す（データとしては残っている） |
| 画像を Issue に貼ると、トークンに Contents の書き込み権限が要る | 既定は貼らない。貼るときだけ `GITHUB_ISSUE_ATTACH_SHOT=true` と権限追加をセットで行う | 最小権限。起票のためだけの鍵で、コードも設定も書き換えられる状態を既定にしない | 常に貼る（既定で広い権限を要求することになる）／貼れないままにする（画像が要望の主役のことがある） |

### 7-2. 一括操作と要望の一生の例外判断 (2026-08-15 追記)

| 場面の1文 | 選んだ形 | 決め手の軸 | 却下した候補と理由 |
| --- | --- | --- | --- |
| 1件ずつしか Issue にできず使いにくいと申告があった | 一覧をカードから表へ変え、チェックボックスで選んでまとめて実行する | 主目的が「読む」から「選んで実行する」へ移った。件数が増えるほど、次に押すものを決める手がかり（起票の状態）が主役になる | カードのまま一括ボタンを足す（何を選んでいるかが1画面で見えない）／表とカードの併用（同じ操作が2箇所に分かれ、守りを二重に書く） |
| 何度押しても・同時に押しても Issue を増やしたくない | 計画で既番号を新規にしない ＋ 60秒で切れる作業中の印 ＋ 番号の一意索引の3段 | 取り消せるか。GitHub に立った Issue は消しても通知と履歴が残る | 画面でボタンを消すだけ（別のタブ・再送で抜ける）／一意索引だけ（先に2本立ってから片方が捨てられる） |
| 内容が変わっていない件を送らずに済ませたい | Issue に載せた内容の指紋（SHA-256）を保存し、一致したら通信しない。一覧の「更新あり」表示だけは時刻の比較で出す | 情報量。指紋の計算には診断情報まで読む必要があり、一覧で全件読むと開かなくなる | 中身をそのまま保存して比較（1件数十KBで DB が倍になる）／毎回送る（Issue の履歴と通知だけが増え、読む人には何も足さない） |
| 「削除」を押した人が、戻せないことに気づいていない | 既定の削除を廃棄（論理削除）にし、完全削除は名前・導線・権限を分けて二段階で確認する | 取り消せるか。押し間違いは必ず起きる前提で、既定を戻せる側に倒す | 確認ダイアログだけ付けた物理削除（読まずに押される）／全部を論理削除で済ませる（個人情報を消してほしいという求めに応えられない） |
| 完全削除しても、すでに立った Issue は消せない | Issue は消さず「元データは削除済み・管理画面のリンクは開いても見つからない」と書き残して閉じる | 取り消せるか。GitHub の Issue は通知メールも履歴も残り、消しても無かったことにはならない | Issue も削除する（消したふりになる。delete 権限まで鍵に持たせることにもなる）／何も書かない（リンクを開いた人が理由の分からない 404 に当たる） |
| 状態を戻したときに、閉じた Issue を開き直すか | 自動では開き直さない。管理者が一括送信で「閉じている Issue も開き直す」に印を付けたときだけ | どちらを正とするか。GitHub 側で「対応しない」と判断して閉じたものが、管理画面の操作で勝手に復活してよいとは限らない | 常に開き直す（GitHub 側の判断を上書きする）／開き直せない（GitHub で作業を再開できない） |
