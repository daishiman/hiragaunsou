# 残課題リスト

初回リリース後に見つかった課題を、業務への影響が大きい順に並べる。
着手するときは項目に「着手中」を付け、完了したら消して git 履歴に残す。

## このファイルの書き方(2つの作業が並行したとき、片方の記録が消えないように)

このファイルは複数の作業が同時に書き換えるため、2回続けて突き合わせが必要になった。
原因は「番号を連番で振ること」と「既存項目の説明文そのものを書き換えること」の2つだったので、
以降は次の3つを守る。

1. **新しい項目に連番を振らない。** 該当セクションの末尾に `### 新: タイトル — 判定` として足す。
   通し番号は棚卸しのときにまとめて振り直す(別々の作業が同じ番号を使う事故を防ぐ)。
2. **既存項目の説明文を書き換えず、その項目の下に日付付きで足す。**
   例: `- (2026-08-08 追記: 取込が失敗していた原因を直した)`。
   段落ごと書き直すと、同じ段落を触った作業同士が必ずぶつかる。
3. **項目を消すのは棚卸しのときだけ。** 消した理由は末尾の「消した項目」に必ず残す
   (何が終わったのかが後から分からなくなるため)。

検討して**採らなかった**手当てと理由:

- **項目ごとにファイルを分ける** — ぶつからなくなる代わりに、一覧を1枚で読めなくなる。
  このリストは依頼者への報告にそのまま添えるものなので、1枚であることの価値が上回る。
- **突き合わせを自動で「両方残す」設定にする(git の union マージ)** — このファイルは
  「終わった項目を消す」ことが通常運転なので、消した行が自動で復活してしまう。害のほうが大きい。
- **課題管理をGitHubのIssueに移す** — 依頼者が読む場所が増える。いまは1ファイルで足りている。

**2026-08-08 に全項目を棚卸しした。** 各項目に次のいずれかの判定を付けている。

- **実装する** — 順番待ち。いつ着手するかだけの問題。
- **待つ** — 着手条件が満たされるまで動かさない。条件を各項目に書く。
- **確認待ち** — 業務側に事実を聞かないと作れない。聞く相手と内容を書く。
- **完了・削除** — 実装済みまたは不要になったもの(この版で本文から消した。下の「この棚卸しで消した項目」に理由を残す)。
