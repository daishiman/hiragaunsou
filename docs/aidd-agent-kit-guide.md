# AI開発エージェントキット(aidd-agent-kit)解説

このドキュメントは `aidd-agent-kit/` が「何を」「どういう仕組みで」やっているのかを、人に説明できる粒度でまとめたものです。作成元: 株式会社TierMind。

---

## 1. 一言でいうと

**Claude Code に「アプリ開発を最初から最後まで、決まった手順とプロの基準で進めさせる」ための拡張キット**です。

利用者は `/build-app 会議室の予約アプリを作って` のように一言頼むだけで、要件整理 → デザイン → 実装 → デプロイ → 品質チェック → リリース判定 までを、Claude が自律的に、しかし勝手な省略なしに進めます。

キットの中身は3種類の部品でできています。

| 部品 | 個数 | 役割 |
|---|---|---|
| コマンド (`commands/`) | 1個 | `/build-app` — 司令塔エージェントを呼び出す入口 |
| エージェント (`agents/`) | 1個 | `app-orchestrator` — 全工程を指揮する司令塔 |
| スキル (`skills/`) | 16個 | 各工程の「プロのノウハウ」を凝縮した手順書・部品集 |

---

## 2. 全体アーキテクチャ:誰が何をするか

```
ユーザー
  │  "/build-app 勤怠管理アプリを作って"
  ▼
commands/build-app.md
  │  役割: 要件が空なら3点だけ質問し、
  │  必ず Agent ツールで app-orchestrator を起動する
  ▼
agents/app-orchestrator.md  ← 司令塔(本体)
  │  役割: フェーズゲート制で工程を進行し、
  │  各フェーズで必要な skill を Skill ツールで明示的にロードする
  ▼
skills/*  ← 16個のノウハウ集(SKILL.md + 参照資料 + テンプレ + 実行スクリプト)
     Phase0: app-excellence
     Phase1: jp-web-design, ux-design
     Phase2: workers-best-practices, testing-excellence, (条件付き)better-auth-google-gate 等
     Phase3: cloudflare-secure-deploy, wrangler
     Phase4: launch-security, testing-excellence, web-perf, llm-cost-simulator
```

ポイントは、**エージェントとスキルの役割分担が明確に分離されている**ことです。

- **エージェント(app-orchestrator)** は「いつ・どのスキルを・どの順番で読むか」という**進行台本**だけを持っています。実装の細かいノウハウそのものは書いていません。
- **スキル** は「実際にどう作るか」という**専門知識**そのものです。ただし単独では発火せず、エージェントに明示的に呼ばれて初めて読み込まれます。

`app-orchestrator.md` の冒頭にある「絶対原則」がこの設計思想を端的に表しています。

> スキルは自動発火しない。この定義に書かれたタイミングで、必ず Skill ツールを自分で呼んでロードする。「読んだつもり」で進めることを禁止する。

これは、AIが「もう知っているから」と自己判断でノウハウを省略してしまう(=知識の陳腐化や思い込みで手抜きする)リスクを、**手順として強制的に塞いでいる**仕組みです。

---

## 3. 動作の仕組み:フェーズゲート制

`app-orchestrator` は Phase 0 〜 4 の5段階で進みます。**前フェーズの完了条件を満たすまで次に進めない**のがゲート制の意味です。

### Phase 0: 要件定義・機能分解(必ず最初)
- ロードするスキル: `app-excellence`
- ここで**「要件フラグ」判定**という重要な処理を行います。ユーザーが「認証」と明言していなくても、「社員だけが使う」「ユーザーごとにデータを分ける」といった要件の**実態**から、認証・AI機能・リアルタイム同期・メール送信・公開フォームの要否を自動判定します。判定に迷ったら ON に倒す(=安全側に倒す)ルールになっています。

### Phase 1: デザイン・UX設計
- ロードするスキル: `jp-web-design` + `ux-design`(必ずセット)
- 見た目のルール(配色・組版・コンポーネント)と、使い勝手のルール(行動科学に基づく操作設計)を分業させています。

### Phase 2: 実装
- 必須: `workers-best-practices`(Cloudflare Workers用のコードを書く前に必ず)
- 条件付き: Phase 0 の要件フラグに応じて以下を**該当したら例外なく**ロード

| 要件フラグ | ロードするスキル |
|---|---|
| 認証あり | `better-auth-google-gate` |
| AI機能あり | `llm-api-integration` |
| リアルタイム同期あり | `durable-objects` |
| メール送信あり | `cloudflare-email-service` |
| 公開フォームあり | `turnstile-spin` |
| その他のCloudflare機能 | `cloudflare` |

- さらに `testing-excellence` をロードし、TDD(RED→GREEN→REFACTOR)サイクルで実装を進めます。

### Phase 3: デプロイ
- ロードするスキル: `cloudflare-secure-deploy` + `wrangler`
- DBマイグレーションを先に本番適用してからコードをデプロイする、といった実戦的な手順に厳密に従います。

### Phase 4: 品質ゲート・リリース判定
- 必須: `launch-security`(セキュリティ・エラー処理・コスト・パフォーマンスの統合監査)
- 必須: `testing-excellence`(リリース前網羅テストの観点)
- デプロイ後: `web-perf` で本番URLのCore Web Vitalsを実測
- AI機能ありなら: `llm-cost-simulator` でコストを試算
- **launch-security の監査でCRITICALが1つでも残っていればリリース不可**。修正して再監査するまでゲートは開きません。

## 4. 16個のスキルの詳細

役割ごとに4グループに分類して説明します。それぞれ `skills/<名前>/SKILL.md` が本体で、多くは `references/`(詳細資料)・`assets/`(コピーして使うテンプレ)・`scripts/`(実行可能なツール)を伴います。

### グループA: 進行管理・デザイン(Phase 0-1)

**app-excellence** — アプリ開発全体の進行台本
要件定義→体験設計→機能分解→実装→品質ゲート→リリース判定をPhase0〜7で進める、全体の背骨となるスキル。「機能要望は必ず本質的な課題(L1課題)に立ち返って考える」「ダークパターンが1つでもあればリリース不可」など、判断の優先順位そのものを定義しています。要件定義書・体験設計書・機能マップ・リリース判定書の4種のテンプレート(`assets/T1〜T4`)も内蔵。

**jp-web-design** — 日本語UIのデザインシステム
色は3系統のみ・白背景固定・視覚的主役は1つ、といった「型」を強制することで、素人目にも破綻しないデザインを再現性高く作れるようにしたスキル。実際に検収を通過した「動く正解」のHTML/CSS一式(`assets/reference/`)を教材として持っており、実装時はそれをコピーして使います。

**ux-design** — 行動科学に基づく操作設計
デフォルト効果・ヒックの法則・ピークエンドの法則など、心理学の知見を「賢い既定値」「一括操作は事前選択+その場確認+1クリック実行」のような具体的な実装ルールに翻訳したスキル。React用の再利用可能なフック集(`assets/ux-patterns.tsx`: 下書き自動保存・一括選択・送信キー制御など)をそのまま実装に転用できます。

### グループB: 実装基盤(Phase 2、Cloudflare関連)

**workers-best-practices** — Workersコードの品質基準
Cloudflare Workers用コードを書く/レビューする際の必須スキル。最大の特徴は「事前学習した知識は古い可能性があるので、公式ドキュメントや最新の型定義を検索で取得することを優先する」という方針を明言している点です。floating promise禁止、グローバル状態禁止など11項目のアンチパターン集を持ちます。

**cloudflare** — Cloudflare全製品カタログ
Workers/Pages/D1/R2/AI/セキュリティ製品など70以上の製品それぞれについて `api.md`/`configuration.md`/`gotchas.md`/`patterns.md` の5点セットを持つ巨大な参照ライブラリ。個別スキルがカバーしない機能(Vectorize、Queuesなど)が必要な時の逃げ道として使われます。

**wrangler** — CLIコマンドリファレンス
Cloudflareの公式CLIツール `wrangler` の操作前チェック用スキル。KV/R2/D1/Vectorize/Workers AI等サービスごとのコマンド実例と、「secretの値をコマンド引数に直接書かない」といったセキュリティ上の注意を網羅しています。

**durable-objects** — ステートフルな協調処理の実装
チャットルーム・予約システムなど「状態を持って複数リクエストを協調させる」必要がある機能の実装スキル。「単一のグローバルDOを作らない」「毎リクエストで初期化処理をしない」など7つの絶対ルールと、Vitestでのテスト方法まで含みます。

### グループC: 機能別の実装パターン(Phase 2、要件フラグで条件発火)

**better-auth-google-gate** — Googleログインの自動実装
認証機能が必要な場合に発火。コード・DB・デプロイはAIが自動実行し、Google Cloud ConsoleでのOAuthアプリ作成だけをユーザーに委ねる設計です。APIキーなどの秘密情報をチャットやログに絶対出さないルール、社内限定ログイン(Google Workspace限定)の実装方法、既知の落とし穴集(`references/known-pitfalls.md`)まで揃っています。

**llm-api-integration** — AI機能の組み込み
画像認識・PDF抽出・自動分類・チャットボットなどAI機能が必要な場合に発火。「AIは判断・生成でなく判別にだけ使う」という設計原則、モデル選択とコスト制御(まず安いモデルから)、利用量を可視化する `/usage` ページを必ず作る、といった実務的なノウハウの集合です。

**cloudflare-email-service** — メール送受信の実装
通知メールや問い合わせフォームが必要な場合に発火。Workers bindingとREST API両方の実装方法、SPF/DKIM/DMARCによる到達率対策までカバーします。

**turnstile-spin** — 問い合わせフォームのbot対策
Cloudflare製CAPTCHA「Turnstile」の導入を、12ステップの対話ウィザードとして自動化するスキル。認証確認→ウィジェット作成→組み込み→検証→(必要なら)スキルの永続化まで、実行可能なシェルスクリプト群(`scripts/`)で完結させます。

### グループD: 品質・デプロイ・運用後最適化(Phase 3-4)

**testing-excellence** — テスト戦略全般
TDD(テスト駆動開発)のRED→GREEN→REFACTORサイクルから、E2Eテスト、デプロイ後の本番確認、リリース前の網羅チェックまでを1つに統合したスキル。「たぶん動く」で完了報告することを明確に禁止しています。

**cloudflare-secure-deploy** — 本番デプロイの手順
DBマイグレーションを先に本番適用してからコードをデプロイする、secretsは.envに書かずwranglerで設定する、といった「間違えると事故る」手順を固定化したスキル。32項目の実戦的な落とし穴集(`references/gotchas.md`)を持ちます。

**launch-security** — リリース前の統合監査
「攻撃に耐えるか」「エラー時に正しく振る舞うか」「コストが破綻しないか」「速いか」の4軸を一度に検査するスキル。grep/audit系のスキャンコマンド集、攻撃パターン別の対処表を備え、CRITICALが1件でも残っているとリリースを止める権限を持ちます。

**web-perf** — 表示速度の計測・改善
デプロイ後、本番URLに対してChrome DevTools MCPでCore Web Vitals(LCP・INP・CLSなど)を実測し、具体的な閾値(LCP 2.5秒未満など)と照らして改善点を出すスキル。

**llm-cost-simulator** — AI機能の料金試算
AI機能を使うアプリのコードからAPI呼び出し箇所を洗い出し、静的推定→無料トークンカウント→実測→実費計測、と確度を段階的に上げながらコストを試算するスキル。Pythonスクリプト(`scripts/engine.py`等)が実際に計算し、Markdown・HTML・JSONのレポートを出力します。

---

## 5. インストールと使い方(要約)

- 対象OSごとに `install-mac.command` / `install-windows.bat` を実行すると、`skills/` `agents/` `commands/` の中身が `~/.claude/` にコピーされます。
- Claude Code を再起動すると `/build-app` が使えるようになります。
- 使い方は `/build-app <作りたいものの説明>` のみ。「誰が使うか」「何ができるか」「公開範囲」の3点を含めると迷わず進みます。
- コマンドを使わず「在庫管理のアプリを作りたい」と話しかけるだけでも `app-orchestrator` は自動的に起動する設計です(エージェントの `description` に強いトリガー条件が書かれているため)。

## 6. この設計の面白いポイント(まとめ)

1. **知識と手順の分離**: エージェントは「何をいつ読むか」という薄い進行ロジックだけを持ち、太い専門知識は全てスキル側に置く。これにより、スキルだけを差し替え・追加すれば司令塔のロジックを変えずにノウハウを更新できます。
2. **キーワード一致ではなく要件の実態で判定**: 「認証」と言われなくても「社員だけが使う」なら認証ありと判定する、という設計により、ユーザーが技術用語を知らなくても正しい工程が選ばれます。
3. **ゲートに人間の承認ではなく機械的な完了条件を置く**: 「CRITICALが0件」のような検証可能な基準でフェーズを進めるため、AIの自己申告(「たぶん大丈夫です」)に頼らない仕組みになっています。
4. **知識の鮮度への自覚**: `workers-best-practices` や `cloudflare` などのスキルは「自分の学習知識は古いかもしれないから、まず公式ドキュメントを検索で取得せよ」と明言しており、LLMの知識カットオフ問題に対する対策が組み込まれています。
