# 03. Feature Decomposition — 縦に切り、リスクから食べる

分解の目的は2つ: ①常に「動く全体」を保ちながら育てる ②最大のリスクを最初に潰す。横切り(まずDB全部→次にAPI全部→最後に画面)を禁止し、**縦切り(1ユースケースを画面からDBまで貫通)**で進める。

## §1. ストーリーマッピング

1. **背骨**: T1のL3(to-beシナリオ)を左から右へ、ユーザーの行動順に並べる(例: 入力する→確認する→集計を見る→共有する)
2. **肋骨**: 各行動の下に、それを支えるストーリーを詳細度順に縦に並べる
3. **カット線**: 横線を引いて Slice 0 / 1 / 2… に分ける
   - **Slice 0(Walking Skeleton)**: 背骨全体を最薄で貫通する1本(ログイン→最小入力→最小表示)。豪華さゼロでよい、貫通していることが価値
   - **Slice 1**: North Star指標を動かす最小セット(=MVP)
   - **Slice 2+**: 磨き込み(ピーク/エンド演出、通知、CSV出力等)

## §2. 優先順位の規律

- **最リスク仮説を最初に**: 「これが成り立たないと全部無駄」という仮説(技術: 外部APIで必要データが取れるか / 体験: 現場が本当に30秒で入力するか)を特定し、Slice 0〜1で検証する。技術リスクはスパイク(捨てる前提の検証コード)として先頭に置く
- 迷ったら RICE(Reach×Impact×Confidence÷Effort)で採点し、判断根拠をT3に残す
- 各ストーリーは INVEST(独立・交渉可能・価値がある・見積れる・小さい・テスト可能)を満たすまで割る。1ストーリー=1PR=1デモが理想

## §3. 各スライスの完了定義(DoD)

スライスは以下を全て満たして初めて完了(コードが書けた≠完了):
- [ ] 動くデモをプレビューURLで依頼者に見せられる
- [ ] 6状態(02 §3)のうち該当するものが実装済み
- [ ] ユニットテスト+主要経路のE2Eが緑
- [ ] 計測イベント(04 §5)が発火している
- [ ] T2/T3の該当箇所が現実と一致している(ドキュメントを腐らせない)

## §4. 依存とリスクの取り扱い

- 外部連携・データ移行・権限設計は「あとで」に置かない(後半に置かれた依存は必ず爆発する)。Slice 0〜1に最薄で含める
- 不確実な要望は作らずに検証する: モック画面だけ先に見せる/手動運用で代替してみる(Wizard of Oz)。**作らずに学べるものは作らない**
- スコープ追加は新カードとしてマップに追加し、カット線を引き直して依頼者と再合意(既存スライスに滑り込ませない)

**ゲート条件(T3)**: Slice 0が定義済み/最リスク仮説が明記されSlice 0〜1に含まれる/全ストーリーがINVESTを満たす。
